# 28 - 系统错误排查与日志分析

> 系统出了问题不可怕，可怕的是不知道如何找到问题所在。本章将系统性地介绍 Arch Linux 下的错误排查方法论，从日志分析到启动修复，从硬件诊断到性能分析，帮助你建立完整的故障排查能力。掌握这些技能后，你将有信心面对各种系统问题。

---

## 28.1 排错思维方法论

排查问题应遵循系统性的思维流程：

```
1. 复现问题 → 明确问题的触发条件
2. 缩小范围 → 确定是硬件、内核、驱动、服务还是应用层问题
3. 查看日志 → journalctl、dmesg、应用日志
4. 搜索信息 → Arch Wiki、论坛、Bug Tracker
5. 尝试修复 → 从最小改动开始
6. 验证修复 → 确认问题已解决且无副作用
7. 记录方案 → 供日后参考
```

排查的核心原则：

| 原则 | 说明 |
|-----|------|
| 最近改了什么 | 问题通常由最近的变更引起 |
| 二分法 | 逐步缩小问题范围 |
| 最小复现 | 用最简单的方式复现问题 |
| 先看日志 | 日志是最重要的线索来源 |
| 一次只改一个 | 避免同时修改多个变量 |

## 28.2 journalctl 深入使用

`journalctl` 是 systemd 的日志查看工具，是排查问题的第一利器。

### 28.2.1 基本使用

```bash
# 查看所有日志
journalctl

# 实时跟踪日志
journalctl -f

# 查看本次启动的日志
journalctl -b

# 查看上次启动的日志
journalctl -b -1

# 查看倒数第三次启动的日志
journalctl -b -2

# 列出所有启动记录
journalctl --list-boots
```

### 28.2.2 按时间过滤

```bash
# 指定起始时间
journalctl --since "2024-01-15 10:00:00"

# 指定时间范围
journalctl --since "2024-01-15" --until "2024-01-16"

# 相对时间
journalctl --since "1 hour ago"
journalctl --since "30 min ago"
journalctl --since yesterday
journalctl --since today
```

### 28.2.3 按服务过滤

```bash
# 查看特定服务的日志
journalctl -u nginx
journalctl -u sshd

# 多个服务
journalctl -u nginx -u php-fpm

# 实时跟踪服务日志
journalctl -u docker -f

# 查看特定 PID 的日志
journalctl _PID=1234

# 查看特定用户的日志
journalctl _UID=1000

# 查看特定可执行文件的日志
journalctl /usr/bin/python
```

### 28.2.4 按优先级过滤

日志优先级（严重性递减）：

| 级别 | 数字 | 含义 |
|-----|------|------|
| emerg | 0 | 系统不可用 |
| alert | 1 | 必须立即处理 |
| crit | 2 | 严重错误 |
| err | 3 | 错误 |
| warning | 4 | 警告 |
| notice | 5 | 一般通知 |
| info | 6 | 信息 |
| debug | 7 | 调试 |

```bash
# 只看错误及以上级别
journalctl -p err
journalctl -p 3

# 只看警告及以上
journalctl -p warning

# 特定范围
journalctl -p warning..err

# 本次启动的错误
journalctl -b -p err
```

### 28.2.5 持久化日志

默认情况下，journald 日志存储在内存中（`/run/log/journal/`），重启后丢失。

```bash
# 启用持久化存储
sudo mkdir -p /var/log/journal
sudo systemd-tmpfiles --create --prefix /var/log/journal

# 或编辑 /etc/systemd/journald.conf
# [Journal]
# Storage=persistent
```

编辑 `/etc/systemd/journald.conf`：

```ini
[Journal]
Storage=persistent
Compress=yes
SystemMaxUse=500M
SystemMaxFileSize=50M
MaxRetentionSec=1month
```

```bash
# 重启 journald
sudo systemctl restart systemd-journald
```

### 28.2.6 日志大小管理

```bash
# 查看日志占用空间
journalctl --disk-usage

# 清理日志（保留最近 2 天）
sudo journalctl --vacuum-time=2d

# 清理日志（限制总大小 500M）
sudo journalctl --vacuum-size=500M

# 清理日志（保留最近 5 个文件）
sudo journalctl --vacuum-files=5

# 验证日志完整性
journalctl --verify
```

### 28.2.7 JSON 输出与高级格式

```bash
# JSON 格式输出
journalctl -o json
journalctl -o json-pretty

# 简洁格式
journalctl -o short-precise

# 只输出消息内容
journalctl -o cat

# 配合 jq 过滤
journalctl -o json | jq 'select(.PRIORITY == "3") | .MESSAGE'

# 导出日志
journalctl -b > /tmp/boot_log.txt
journalctl -u nginx -o json > /tmp/nginx_log.json
```

### 28.2.8 内核日志

```bash
# 只看内核消息
journalctl -k
journalctl -k -b  # 本次启动的内核消息

# 等同于 dmesg
journalctl --dmesg
```

## 28.3 dmesg 内核日志分析

`dmesg` 显示内核环形缓冲区的消息，主要包含硬件检测、驱动加载等信息。

```bash
# 查看内核日志
dmesg
dmesg -H  # 人类可读格式（带颜色和时间戳）
dmesg -T  # 显示人类可读的时间戳

# 实时跟踪
dmesg -w

# 按级别过滤
dmesg -l err
dmesg -l err,warn
dmesg -l emerg,alert,crit,err

# 按设施过滤
dmesg -f kern  # 内核消息
dmesg -f daemon  # 守护进程
```

常见需要关注的 dmesg 信息：

```bash
# 硬件错误
dmesg | grep -i error
dmesg | grep -i fail
dmesg | grep -i "out of memory"

# 驱动问题
dmesg | grep -i firmware
dmesg | grep -i "not found"

# USB 设备
dmesg | grep -i usb

# 存储设备
dmesg | grep -iE "(sda|nvme|ata)"

# GPU 相关
dmesg | grep -iE "(drm|gpu|i915|amdgpu|nvidia)"
```

## 28.4 系统启动失败排查

### 28.4.1 无法进入图形界面

```bash
# 切换到 TTY（Ctrl+Alt+F2 到 F6）

# 检查显示管理器状态
systemctl status sddm
systemctl status gdm
systemctl status lightdm

# 查看 Xorg 日志
cat /var/log/Xorg.0.log | grep "(EE)"

# 查看 Wayland 日志
journalctl -b --user -u sway
journalctl -b | grep -i wayland

# 常见原因与修复
# 1. 显卡驱动问题
sudo pacman -S xf86-video-vesa  # 通用显卡驱动（应急）

# 2. 显示管理器配置错误
sudo systemctl disable sddm
startx  # 手动启动 Xorg 测试

# 3. 权限问题
ls -la ~/.Xauthority
rm ~/.Xauthority  # 删除后重新登录
```

### 28.4.2 内核 panic

内核 panic 是最严重的错误，系统会完全停止响应。

```bash
# 查看上次启动的 panic 信息
journalctl -b -1 -p emerg

# 常见原因
# 1. 内核模块不兼容 → 尝试 LTS 内核
sudo pacman -S linux-lts linux-lts-headers

# 2. 文件系统损坏 → live USB 修复
# 3. 内存损坏 → memtest86+

# 添加内核参数用于调试（在 GRUB 启动菜单按 e 编辑）
# 在 linux 行末尾添加：
# systemd.log_level=debug
# systemd.log_target=kmsg
```

### 28.4.3 initramfs 问题

```bash
# 重建 initramfs
sudo mkinitcpio -P

# 查看当前 initramfs 配置
cat /etc/mkinitcpio.conf

# 常见问题：缺少必要的 HOOKS
# 确保以下 HOOKS 存在：
# HOOKS=(base udev autodetect modconf kms keyboard keymap consolefont block filesystems fsck)

# 列出 initramfs 内容（调试）
lsinitcpio /boot/initramfs-linux.img

# 如果加密卷无法解锁，确保 encrypt hook 存在
# HOOKS=(... block encrypt filesystems ...)
```

### 28.4.4 fstab 错误

fstab 配置错误会导致系统无法挂载分区，启动失败或进入紧急模式。

```bash
# 进入紧急模式后
# 以读写方式重新挂载根分区
mount -o remount,rw /

# 编辑 fstab
nano /etc/fstab

# 验证 fstab 语法
findmnt --verify --verbose

# 常见错误
# 1. UUID 错误 → 用 blkid 确认
blkid

# 2. 文件系统类型错误
# 3. 挂载点不存在 → 创建目录
mkdir -p /mnt/data

# 4. 使用 nofail 选项防止非关键分区阻止启动
# /dev/sdb1  /mnt/data  ext4  defaults,nofail  0  2
```

### 28.4.5 文件系统损坏

```bash
# ext4 文件系统检查（必须在未挂载状态下进行）
sudo umount /dev/sda1
sudo e2fsck -f /dev/sda1

# btrfs 文件系统检查
sudo btrfs check /dev/sda1
sudo btrfs scrub start /

# XFS 文件系统检查
sudo xfs_repair /dev/sda1

# 如果根分区损坏，使用 live USB 启动后修复
```

## 28.5 服务故障排查

### 28.5.1 systemctl 状态分析

```bash
# 查看服务状态
systemctl status nginx

# 状态解读
# ● nginx.service - A high performance web server
#      Loaded: loaded (/usr/lib/systemd/system/nginx.service; enabled)
#      Active: failed (Result: exit-code) since ...
#     Process: 1234 ExecStart=/usr/bin/nginx (code=exited, status=1/FAILURE)
#    Main PID: 1234 (code=exited, status=1/FAILURE)

# 查看失败的服务
systemctl --failed

# 重置失败状态
sudo systemctl reset-failed

# 查看服务的完整日志
journalctl -u nginx --no-pager

# 查看服务启动耗时
systemd-analyze blame

# 查看启动关键链
systemd-analyze critical-chain
```

### 28.5.2 依赖关系检查

```bash
# 查看服务依赖
systemctl list-dependencies nginx

# 查看反向依赖
systemctl list-dependencies --reverse nginx

# 查看服务属性
systemctl show nginx

# 查看服务文件内容
systemctl cat nginx

# 编辑服务文件（创建 override）
sudo systemctl edit nginx
# 或编辑完整文件
sudo systemctl edit --full nginx
```

### 28.5.3 资源限制问题

```bash
# 查看服务资源限制
systemctl show nginx -p LimitNOFILE -p LimitNPROC -p MemoryMax

# 如果服务因资源限制失败，创建 override
sudo systemctl edit nginx
```

```ini
[Service]
LimitNOFILE=65536
LimitNPROC=4096
MemoryMax=2G
```

```bash
# 检查 cgroup 资源使用
systemd-cgtop

# 查看特定服务的 cgroup
systemctl status nginx | grep CGroup
cat /sys/fs/cgroup/system.slice/nginx.service/memory.current
```

## 28.6 硬件故障排查

### 28.6.1 硬盘 SMART 检测

```bash
# 安装 smartmontools
sudo pacman -S smartmontools

# 查看 SMART 信息
sudo smartctl -a /dev/sda

# 健康状态快速检查
sudo smartctl -H /dev/sda

# 运行短时自检（约 2 分钟）
sudo smartctl -t short /dev/sda

# 运行长时自检（可能需要数小时）
sudo smartctl -t long /dev/sda

# 查看自检结果
sudo smartctl -l selftest /dev/sda

# NVMe SMART 信息
sudo smartctl -a /dev/nvme0
sudo nvme smart-log /dev/nvme0
```

关键 SMART 属性：

| 属性 ID | 名称 | 危险阈值 |
|--------|------|---------|
| 5 | Reallocated Sector Count | > 0 需警惕 |
| 187 | Reported Uncorrectable Errors | > 0 需警惕 |
| 188 | Command Timeout | 持续增长 |
| 197 | Current Pending Sector | > 0 需警惕 |
| 198 | Offline Uncorrectable | > 0 需关注 |

### 28.6.2 内存测试（memtest86+）

```bash
# 安装
sudo pacman -S memtest86+-efi

# UEFI 系统安装到 ESP
sudo memtest86+-efi --install

# 或手动复制到 ESP
sudo cp /boot/memtest86+/memtest.efi /boot/EFI/memtest86+/memtest.efi
```

GRUB 菜单项：

```
menuentry "Memtest86+" {
    linux /boot/memtest86+/memtest.bin
}
```

> 内存测试应在系统关闭后单独运行，完整测试通常需要数小时。建议至少运行 2 遍。

### 28.6.3 CPU 温度监控

```bash
# 安装 lm_sensors
sudo pacman -S lm_sensors
sudo sensors-detect
sensors

# 持续监控
watch -n 1 sensors

# 压力测试时监控
sudo pacman -S stress
stress --cpu $(nproc) --timeout 60 &
watch -n 1 sensors

# 查看 CPU 频率
watch -n 1 "cat /proc/cpuinfo | grep MHz"

# 使用 turbostat（Intel CPU）
sudo turbostat --interval 1
```

### 28.6.4 电源问题

```bash
# 查看电池状态
upower -i /org/freedesktop/UPower/devices/battery_BAT0

# ACPI 信息
acpi -V

# 查看电源事件日志
journalctl -b | grep -i "battery\|power\|acpi\|suspend"

# 挂起/休眠问题排查
# 测试挂起
sudo systemctl suspend
# 如果无法唤醒，检查日志
journalctl -b -1 | grep -i "suspend\|resume\|sleep"

# 休眠问题
# 确保 swap 分区足够大（至少等于 RAM）
swapon --show
```

## 28.7 网络故障排查

```bash
# 基本连通性检查
ping -c 4 archlinux.org
ping -c 4 8.8.8.8  # 测试网络连接（排除 DNS 问题）

# DNS 测试
nslookup archlinux.org
dig archlinux.org
resolvectl status

# 查看网络接口
ip addr show
ip link show

# 查看路由
ip route show

# 查看活跃连接
ss -tulnp

# 端口测试
nc -zv example.com 443

# 追踪路由
traceroute archlinux.org
mtr archlinux.org

# 抓包分析
sudo tcpdump -i eth0 -n port 80
sudo tcpdump -i any -w /tmp/capture.pcap

# NetworkManager 日志
journalctl -u NetworkManager -f

# WiFi 问题
nmcli device wifi list
nmcli device wifi connect "SSID" password "PASSWORD"
nmcli connection show
iwconfig
```

常见网络问题速查：

| 症状 | 可能原因 | 排查命令 |
|-----|---------|---------|
| 完全无网络 | 网卡未启用 | `ip link show` |
| 能 ping IP 不能 ping 域名 | DNS 配置错误 | `resolvectl status` |
| 间歇性断连 | 电源管理关闭网卡 | `iw dev wlan0 get power_save` |
| 速度慢 | 链路速率问题 | `ethtool eth0` |
| 连接被拒绝 | 防火墙 | `sudo iptables -L -n` |

## 28.8 包管理故障

### 28.8.1 pacman 数据库锁定

```bash
# 症状：unable to lock database
# 确认没有其他 pacman 进程在运行
ps aux | grep pacman

# 如果确认无其他 pacman 进程，删除锁文件
sudo rm /var/lib/pacman/db.lck
```

### 28.8.2 密钥环问题

```bash
# 症状：PGP 签名验证失败

# 重新初始化密钥环
sudo pacman-key --init
sudo pacman-key --populate archlinux

# 刷新密钥
sudo pacman-key --refresh-keys

# 如果时间不对导致签名验证失败
sudo timedatectl set-ntp true
sudo hwclock --systohc
```

### 28.8.3 依赖冲突

```bash
# 症状：conflicting files / dependency conflicts

# 查找文件属于哪个包
pacman -Qo /path/to/conflicting/file

# 强制覆盖（谨慎使用）
sudo pacman -S package --overwrite '/path/to/file'

# 查看依赖关系
pactree package_name
pactree -r package_name  # 反向依赖

# 检查孤立包
pacman -Qdt
# 清理孤立包
sudo pacman -Rns $(pacman -Qdtq)
```

### 28.8.4 部分升级修复

Arch Linux 不支持部分升级，部分升级可能导致库版本不匹配。

```bash
# 症状：程序报错找不到 .so 文件
# error while loading shared libraries: libxxx.so.X

# 修复方法：执行完整系统升级
sudo pacman -Syu

# 如果 pacman 本身损坏，使用静态编译版本
# 从 Arch ISO 中获取或使用 pacman-static（AUR）
yay -S pacman-static
sudo pacman-static -Syu

# 查看哪些包需要更新
checkupdates

# 查看依赖某个库的所有包
pacman -Qi package | grep "Required By"
```

## 28.9 Arch Linux 系统修复

### 28.9.1 Live USB 挂载修复

当系统无法启动时，使用 Arch 安装 USB 启动进入 live 环境。

```bash
# 1. 从 Arch ISO USB 启动

# 2. 识别分区
lsblk
fdisk -l

# 3. 挂载系统分区
mount /dev/sda2 /mnt          # 根分区
mount /dev/sda1 /mnt/boot     # 启动分区（EFI）

# 如果是 btrfs
mount -o subvol=@ /dev/sda2 /mnt
mount -o subvol=@home /dev/sda2 /mnt/home

# 如果是加密分区
cryptsetup open /dev/sda2 cryptroot
mount /dev/mapper/cryptroot /mnt

# 如果是 LVM
vgscan
vgchange -ay
mount /dev/vg0/root /mnt
```

### 28.9.2 chroot 修复

```bash
# 使用 arch-chroot（推荐）
arch-chroot /mnt

# 或手动 chroot
mount -t proc /proc /mnt/proc
mount -t sysfs /sys /mnt/sys
mount --rbind /dev /mnt/dev
mount --rbind /run /mnt/run
chroot /mnt /bin/bash

# 进入 chroot 后可以执行各种修复操作
# 修复 pacman
pacman -Syu

# 重装内核
pacman -S linux linux-headers

# 修复引导
grub-install --target=x86_64-efi --efi-directory=/boot --bootloader-id=GRUB
grub-mkconfig -o /boot/grub/grub.cfg

# 修复 fstab
nano /etc/fstab

# 修复网络配置
nano /etc/resolv.conf

# 退出 chroot
exit
umount -R /mnt
reboot
```

### 28.9.3 pacman 缓存降级

```bash
# 列出缓存中的包版本
ls /var/cache/pacman/pkg/ | grep package_name

# 降级特定包
sudo pacman -U /var/cache/pacman/pkg/package_name-old_version.pkg.tar.zst

# 使用 downgrade 工具（AUR）
yay -S downgrade
sudo downgrade package_name

# 将包加入忽略列表防止自动升级
# 编辑 /etc/pacman.conf
# IgnorePkg = package_name

# 批量降级
sudo pacman -U /var/cache/pacman/pkg/{pkg1,pkg2,pkg3}-version.pkg.tar.zst
```

### 28.9.4 重建 initramfs

```bash
# 重建所有内核的 initramfs
sudo mkinitcpio -P

# 重建特定内核的 initramfs
sudo mkinitcpio -p linux
sudo mkinitcpio -p linux-lts

# 如果 mkinitcpio 报错，检查配置
cat /etc/mkinitcpio.conf

# 常见修复：确保所有必要的 HOOKS 存在
# HOOKS=(base udev autodetect modconf kms keyboard keymap consolefont block filesystems fsck)

# 如果使用加密，添加 encrypt hook
# HOOKS=(... block encrypt filesystems ...)

# 如果使用 LVM
# HOOKS=(... block lvm2 filesystems ...)

# 如果使用 btrfs
# MODULES=(btrfs)
```

## 28.10 coredump 分析

当程序崩溃时，systemd 会自动收集 coredump。

### 28.10.1 coredumpctl 基本使用

```bash
# 列出所有 coredump
coredumpctl list

# 查看最近的 coredump
coredumpctl info

# 查看特定程序的 coredump
coredumpctl info firefox

# 查看特定 PID 的 coredump
coredumpctl info 12345

# 将 coredump 转储到文件
coredumpctl dump firefox -o /tmp/firefox.core
```

### 28.10.2 使用 GDB 分析

```bash
# 安装调试工具
sudo pacman -S gdb

# 使用 coredumpctl 直接启动 gdb
coredumpctl gdb firefox

# 在 gdb 中查看堆栈
(gdb) bt        # backtrace
(gdb) bt full   # 完整堆栈
(gdb) info threads  # 线程信息
(gdb) thread apply all bt  # 所有线程的堆栈
```

### 28.10.3 安装调试符号

```bash
# 启用 debuginfod（自动下载调试符号）
export DEBUGINFOD_URLS="https://debuginfod.archlinux.org"

# 添加到 ~/.bashrc 或 ~/.zshrc 持久化
echo 'export DEBUGINFOD_URLS="https://debuginfod.archlinux.org"' >> ~/.bashrc
```

### 28.10.4 coredump 配置

## 28.11 strace 和 ltrace 调试

### 28.11.1 strace

strace 跟踪进程的系统调用和信号。

```bash
# 安装
sudo pacman -S strace

# 跟踪程序执行
strace ls

# 跟踪正在运行的进程
sudo strace -p 1234

# 只跟踪特定类型的系统调用
strace -e trace=open,read,write ls
strace -e trace=network curl example.com
strace -e trace=file ls

# 统计系统调用
strace -c ls

# 显示时间戳
strace -t ls      # 秒
strace -tt ls     # 微秒
strace -T ls      # 每个调用的耗时

# 跟踪子进程
strace -f command

# 将输出保存到文件
strace -o /tmp/strace.log ls

# 显示字符串的完整内容（默认截断为 32 字节）
strace -s 256 ls
```

常见用途：

```bash
# 查看程序打开了哪些文件
strace -e trace=openat program 2>&1 | grep -v ENOENT

# 查看程序的网络连接
strace -e trace=connect,sendto,recvfrom program

# 定位程序启动缓慢的原因
strace -T -e trace=file program 2>&1 | sort -t= -k2 -rn | head

# 查看程序为什么失败
strace -e trace=openat program 2>&1 | grep "ENOENT\|EACCES"
```

### 28.11.2 ltrace

ltrace 跟踪动态库函数调用。

```bash
# 安装
sudo pacman -S ltrace

# 基本使用
ltrace ls

# 跟踪特定库函数
ltrace -e malloc+free ls

# 统计
ltrace -c ls

# 跟踪运行中的进程
sudo ltrace -p 1234
```

## 28.12 perf 性能分析入门

perf 是 Linux 内核自带的强大性能分析工具。

```bash
# 安装
sudo pacman -S perf

# 统计程序执行的硬件事件
sudo perf stat ls

# 采样分析
sudo perf record -g ./my_program
sudo perf report

# 实时 top 视图
sudo perf top

# 分析特定事件
sudo perf stat -e cache-misses,cache-references,instructions,cycles ./my_program

# 跟踪特定进程
sudo perf record -g -p 1234 sleep 10
sudo perf report

# 生成火焰图
sudo perf record -g ./my_program
sudo perf script > /tmp/perf.data.txt
# 使用 FlameGraph 工具生成 SVG
```

火焰图生成完整流程：

```bash
# 获取 FlameGraph 工具
git clone https://github.com/brendangregg/FlameGraph /tmp/FlameGraph

# 采集数据
sudo perf record -F 99 -g -p $(pgrep my_program) -- sleep 30

# 生成火焰图
sudo perf script | /tmp/FlameGraph/stackcollapse-perf.pl | /tmp/FlameGraph/flamegraph.pl > flamegraph.svg
```

## 28.14 本章测验

> [!example] 📝 自测题目

> [!question]- 选择题 1：使用 journalctl 查看上一次启动的日志，正确的命令是？
> - A. `journalctl -b 1`
> - B. `journalctl -b -1`
> - C. `journalctl --last-boot`
> - D. `journalctl -b previous`
>
> > [!success]- 点击查看答案
> > **B**
> > `journalctl -b -1` 查看上一次启动的日志。-b 0 或 -b 是本次启动，-b -1 是上次，-b -2 是倒数第三次。

> [!question]- 选择题 2：journalctl 中，日志优先级 "err" 对应的数字级别是？
> - A. 1
> - B. 2
> - C. 3
> - D. 4
>
> > [!success]- 点击查看答案
> > **C**
> > 日志优先级从高到低：emerg(0)、alert(1)、crit(2)、err(3)、warning(4)、notice(5)、info(6)、debug(7)。

> [!question]- 选择题 3：默认情况下，journald 的日志存储在哪里？
> - A. /var/log/journal/（持久化存储）
> - B. /run/log/journal/（内存，重启后丢失）
> - C. /var/log/messages
> - D. /tmp/journal/
>
> > [!success]- 点击查看答案
> > **B**
> > 默认情况下 journald 日志存储在内存中（/run/log/journal/），重启后丢失。需要创建 /var/log/journal/ 目录或设置 Storage=persistent 才能持久化。

> [!question]- 选择题 4：系统无法启动进入紧急模式后，第一步应该做什么？
> - A. 直接修改 /etc/fstab
> - B. 以读写方式重新挂载根分区：`mount -o remount,rw /`
> - C. 重启系统
> - D. 重装系统
>
> > [!success]- 点击查看答案
> > **B**
> > 进入紧急模式后根分区通常是只读挂载的，需要先执行 `mount -o remount,rw /` 以读写方式重新挂载，之后才能编辑配置文件进行修复。

> [!question]- 判断题 5：Arch Linux 支持部分升级（只升级个别包而不做完整系统更新）。
> - A. ✓ 正确
> - B. ✗ 错误
>
> > [!success]- 点击查看答案
> > **B. ✗ 错误**
> > Arch Linux 不支持部分升级。部分升级可能导致库版本不匹配，应始终使用 `pacman -Syu` 进行完整系统升级。

> [!question]- 选择题 6：使用 strace 跟踪一个程序打开了哪些文件，应该使用什么参数？
> - A. `strace -e trace=file program`
> - B. `strace -e trace=network program`
> - C. `strace -e trace=openat program`
> - D. A 和 C 都可以
>
> > [!success]- 点击查看答案
> > **D**
> > `strace -e trace=file` 跟踪所有文件相关系统调用，`strace -e trace=openat` 只跟踪 openat 调用。两者都可以查看程序打开了哪些文件。

> [!question]- 选择题 7：从 Live USB 启动后，进入已安装系统进行修复的推荐命令是？
> - A. `chroot /mnt /bin/bash`
> - B. `arch-chroot /mnt`
> - C. `mount --bind / /mnt && chroot /mnt`
> - D. `systemd-nspawn -D /mnt`
>
> > [!success]- 点击查看答案
> > **B**
> > `arch-chroot /mnt` 是推荐的方式，它会自动处理 /proc、/sys、/dev 等虚拟文件系统的挂载，比手动 chroot 更方便可靠。

> [!question]- 判断题 8：SMART 属性中 Reallocated Sector Count 大于 0 表示硬盘可能存在潜在故障风险。
> - A. ✓ 正确
> - B. ✗ 错误
>
> > [!success]- 点击查看答案
> > **A. ✓ 正确**
> > Reallocated Sector Count（重分配扇区计数）大于 0 说明硬盘已经有坏扇区并进行了重映射，这是硬盘健康状况恶化的早期信号。

> [!question]- 选择题 9：pacman 报错 "unable to lock database" 时，确认无其他 pacman 进程后应如何处理？
> - A. 重启系统
> - B. 重装 pacman
> - C. 删除 /var/lib/pacman/db.lck
> - D. 执行 pacman -Sc
>
> > [!success]- 点击查看答案
> > **C**
> > 确认没有其他 pacman 进程在运行后，可以安全地删除锁文件：`sudo rm /var/lib/pacman/db.lck`。

> [!question]- 选择题 10：查看系统启动过程中各服务耗时，应使用什么命令？
> - A. `systemctl status`
> - B. `systemd-analyze blame`
> - C. `journalctl --boot-time`
> - D. `systemctl list-timers`
>
> > [!success]- 点击查看答案
> > **B**
> > `systemd-analyze blame` 列出各服务的启动耗时，按耗时从长到短排序。`systemd-analyze critical-chain` 则显示启动关键链。
