# 并发的硬件基础

## 原理

多线程并发在硬件层面由以下机制支撑：

**缓存一致性协议**（MESI）：多核 CPU 通过总线嗅探维护 L1/L2 缓存一致性。Modified → Exclusive → Shared → Invalid 状态机确保所有核心看到一致的内存视图。

**内存序**（Memory Order）：CPU 和编译器可能重排指令。x86 提供较强保证（Load-Load, Load-Store, Store-Store 不重排），Store-Load 可能重排。ARM 提供较弱保证——需要显式屏障。

**原子操作**：在 x86 上 `LOCK` 前缀锁住内存总线或缓存行，实现原子 RMW（read-modify-write）。`std::sync::atomic` 暴露了 `Ordering::Relaxed/Acquire/Release/AcqRel/SeqCst`。

**Mutex 实现**：`std::sync::Mutex` 底层用 `futex`（Linux）或 `SRWLOCK`（Windows）——先自旋锁（spinlock）尝试几次，失败则陷入内核等待。自旋锁适合临界区极短的场景。

Rust 的 `Send` / `Sync` trait 在编译期阻止数据竞争：`Send` = 可安全转移所有权到另一线程；`Sync` = 可安全地从另一线程通过引用访问。

## 缓存一致性协议（MESI）深度解析

### 为什么需要缓存一致性

现代 CPU 每个核心拥有独立的 L1/L2 缓存。当核心 A 修改了缓存行中的变量 `x`，核心 B 的缓存行中可能仍持有 `x` 的旧值。如果不加干预，两个核心看到的 `x` 值不一致——这就是**缓存一致性问题**。

```text
┌─────────────────────────────────────────────────┐
│                  主内存 (DRAM)                    │
│              x = 42 (address 0x1000)             │
└──────────┬──────────────────┬───────────────────┘
           │                  │
     ┌─────▼─────┐      ┌─────▼─────┐
     │   Core 0   │      │   Core 1   │
     │  L1 Cache  │      │  L1 Cache  │
     │  x = 42 ✓  │      │  x = 42 ✓  │
     └───────────┘      └───────────┘
         时刻 T0: 两个核心都读到 x=42

         ─── Core 0 执行 x = 99 ───

     ┌───────────────────┐      ┌─────▼─────┐
     │   Core 0           │      │   Core 1   │
     │  L1 Cache          │      │  L1 Cache  │
     │  x = 99 (Modified) │      │  x = 42   │ ← 过时！
     └───────────────────┘      │  (Invalid) │
                                 └───────────┘
```

### MESI 状态机

MESI 是最经典的缓存一致性协议，每个缓存行有 4 种状态：

| 状态 | 含义 | 其他核心是否有副本 |
|------|------|-------------------|
| **M** (Modified) | 已修改，仅本核心持有，脏数据 | 无 |
| **E** (Exclusive) | 独占，干净，与主存一致 | 无 |
| **S** (Shared) | 共享，干净，与其他核心一致 | 可能有 |
| **I** (Invalid) | 无效，需要从主存或其他缓存获取 | - |

```text
        本地读命中              本地写命中
    ┌─────────────┐        ┌─────────────┐
    │  E 或 S      │        │  E 或 M      │
    │  → 保持 E/S  │        │  → 保持 M    │
    └─────────────┘        └─────────────┘

        其他核心写入
    ┌─────────────┐
    │  S → I       │
    │  E → I       │
    │  M → I       │ (写回主存)
    └─────────────┘
```

**关键路径——Store 转发（Store Forwarding）**：当核心写入后立即读取同一地址，L1 缓存直接从 store buffer 转发数据，无需等待写入完成。这解释了为什么 x86 的 Store-Load 不能保证顺序——Store 可能在 store buffer 中尚未对其他核心可见。

### 缓存行（Cache Line）大小

典型的 L1 缓存行大小为 **64 字节**。这意味着：
- `false sharing`（伪共享）：两个无关变量位于同一缓存行，导致不必要的缓存失效
- 解决方案：使用 `#[repr(align(64))]` 或 `std::mem::size_of::<T>()` 确保关键字段独占缓存行

```rust
use std::sync::atomic::{AtomicU64, Ordering};

// 伪共享问题：两个原子计数器位于同一缓存行
struct BadLayout {
    reads: AtomicU64,   // offset 0..8
    writes: AtomicU64,  // offset 8..16  ← 同一缓存行！
}

// 解决方案：padding 隔离
#[repr(align(64))]
struct PaddedAtomic {
    value: AtomicU64,
    _padding: [u8; 56],
}

struct GoodLayout {
    reads: PaddedAtomic,   // 独占缓存行
    writes: PaddedAtomic,  // 独占缓存行
}
```

### MESI 在多核系统中的消息传递

MESI 协议通过**总线嗅探（Bus Snooping）**实现。每个核心的缓存控制器监听总线上的事务：

1. **Read 请求**：核心请求读取某地址。如果其他核心持有 Modified 状态，必须先写回主存。
2. **Invalidate 请求**：核心请求写入，通知其他核心将对应缓存行标记为 Invalid。
3. **Write-back**：Modified 状态的缓存行被替换时，必须写回主存。

```text
核心 A 写入 x (地址 0x1000):

  Core A                          Core B
    │                               │
    │── Invalidate(0x1000) ────────►│  Core B 将缓存行标记为 I
    │                               │
    │  x = 99                       │
    │  (状态: M)                    │
    │                               │
    ▼                               ▼
  稍后 Core B 读取 x:
    │                               │
    │◄── Read(0x1000) ──────────────│
    │                               │
    │── Data(x=99) ────────────────►│  Core A 提供数据
    │  (状态: S)                    │  (状态: S)
```

## 内存序（Memory Ordering）深度解析

### 为什么需要内存序

CPU 和编译器为了性能会重排指令。在单线程中，这不影响程序正确性（通过依赖保证最终结果一致）。但在多线程中，一个核心的指令重排可能被另一个核心观察到异常顺序。

```text
时间线示例（两个线程共享变量 a=0, b=0）:

Thread 1:                  Thread 2:
  a = 1                      b = 1
  if (b == 0) print "X"     if (a == 0) print "Y"

可能的输出：X 和 Y 都打印！
因为 a=1 和 b=1 可能被重排到条件判断之后。
```

### 五种内存序详解

```text
Relaxed:     仅保证原子性，不保证顺序
Acquire:     读操作，之后的读写不能重排到此之前
Release:     写操作，之前的读写不能重排到此之后
AcqRel:      同时具有 Acquire + Release 语义
SeqCst:      全局顺序一致性，最严格
```

**Relaxed**：最弱的保证。仅保证单个原子变量的操作原子性，不保证不同变量之间的顺序。

```rust
use std::sync::atomic::{AtomicI32, AtomicBool, Ordering};

static DATA: AtomicI32 = AtomicI32::new(0);
static READY: AtomicBool = AtomicBool::new(false);

// Thread 1
DATA.store(42, Ordering::Relaxed);
READY.store(true, Ordering::Relaxed);

// Thread 2
if READY.load(Ordering::Relaxed) {
    // Relaxed 不保证 DATA 在 READY 之前可见
    // 可能看到 READY=true 但 DATA=0 ！
    let x = DATA.load(Ordering::Relaxed); // 危险！
}
```

**Acquire/Release**：成对使用，建立同步关系。Release 写入之前的所有操作，对 Acquire 读取之后的操作可见。

```rust
use std::sync::atomic::{AtomicBool, Ordering};
use std::sync::Arc;
use std::thread;

let data = Arc::new((AtomicBool::new(false), Vec::<i32>::new()));
let (flag, vec) = (&data.0, &data.1);

// 实际中需要用 Mutex 保护 Vec，这里仅示意原子同步语义

// Thread 1: Producer
flag.store(true, Ordering::Release);  // Release: 之前的写入对其他线程可见

// Thread 2: Consumer
if flag.load(Ordering::Acquire) {     // Acquire: 之后的读取能看到 Release 之前的数据
    // 安全：能保证看到 Thread 1 在 Release 之前的所有写入
}
```

**SeqCst**：最强的保证。所有使用 SeqCst 的操作形成一个全局全序（total order），就像所有核心以相同顺序执行这些操作。

```rust
use std::sync::atomic::{AtomicBool, AtomicI32, Ordering};
use std::thread;

let a = AtomicBool::new(false);
let b = AtomicBool::new(false);
let x = AtomicI32::new(0);
let y = AtomicI32::new(0);

// Thread 1
a.store(true, Ordering::SeqCst);
let r1 = y.load(Ordering::SeqCst);
x.store(r1, Ordering::SeqCst);

// Thread 2
b.store(true, Ordering::SeqCst);
let r2 = x.load(Ordering::SeqCst);
y.store(r2, Ordering::SeqCst);

// SeqCst 保证不可能出现 r1==0 且 r2==0 的情况
// 因为所有 SeqCst 操作形成全局全序
```

### x86 TSO (Total Store Order) 内存模型

x86 采用相对较强的内存模型：

```text
保证：
  Load-Load:    不重排
  Load-Store:   不重排
  Store-Store:  不重排

不保证：
  Store-Load:   可能重排！

┌──────────────────────────────────────┐
│           x86 Store Buffer            │
│                                       │
│  Core 0:   Store x=99  ──► Store Buf │
│            Load x      ◄── Store Buf │ (Store-Load 可重排)
│                                       │
│  Core 1:   观察到的 x 值？             │
│            x 可能仍为旧值               │
└──────────────────────────────────────┘
```

这就是为什么 x86 上 SeqCst 的 Store 需要加 `LOCK` 前缀的 `MFENCE` 或使用 `XCHG` 指令（隐含全屏障）。

### ARM 弱内存序

ARM 提供更弱的内存保证。大多数 Load/Store 之间可以重排，需要显式屏障（`DMB`, `DSB`, `ISB`）。

```text
ARM 屏障指令：
  DMB (Data Memory Barrier):   保证屏障前的内存操作对屏障后可见
  DSB (Data Synchronization Barrier): 等待所有内存操作完成
  ISB (Instruction Synchronization Barrier): 刷新流水线

Rust 中 Ordering::SeqCst 在 ARM 上编译为 DMB ISH + DMB ISHLD
```

## 原子操作底层实现

### x86 的 LOCK 前缀

在 x86 上，原子 RMW 操作通过 `LOCK` 前缀实现：

```text
; fetch_add(1, SeqCst) 的 x86_64 汇编
lock add dword ptr [rcx], 1

; 原理：
; 1. LOCK 前缀锁定缓存行（或总线）
; 2. 执行 read-modify-write 为原子操作
; 3. 其他核心无法同时修改该缓存行

; 对于比较弱的 Ordering（Relaxed），不需要 LOCK 前缀
; 但 x86 的原子 RMW 本身就有完整屏障语义
```

### ARM 的原子操作

ARM 使用 `LDXR`/`STXR`（Load-Exclusive/Store-Exclusive）对：

```text
; fetch_add(1, AcqRel) 的 ARM64 汇编
loop:
    ldaxr   w1, [x0]      ; Load-Acquire Exclusive
    add     w1, w1, #1
    stlxr   w2, w1, [x0]  ; Store-Release Exclusive
    cbnz    w2, loop       ; 如果失败则重试

; Relaxed 版本去掉 a/l 后缀：
; ldxr + add + stxr
```

### std::sync::atomic 的底层

```rust
use std::sync::atomic::{AtomicI32, Ordering};

let a = AtomicI32::new(0);

// Relaxed: 编译为普通指令（x86 上无 LOCK 前缀）
a.fetch_add(1, Ordering::Relaxed);

// Acquire: 编译为 load + lfence（或 x86 上为普通 load，因 x86 Load 不重排）
a.load(Ordering::Acquire);

// Release: 编译为 store + mfence（或 x86 上为普通 store）
a.store(1, Ordering::Release);

// SeqCst: 编译为 load + mfence + store（x86 上需 MFENCE）
a.compare_exchange(0, 1, Ordering::SeqCst, Ordering::SeqCst);
```

## Mutex 内部实现详解

### futex（Fast Userspace Mutex）

Linux 的 `futex` 是用户态和内核态的混合锁：

```text
┌──────────────────────────────────────────┐
│              Mutex 状态                    │
│                                           │
│  Unlocked (0):  无锁                      │
│  Locked (1):    已锁，无等待者              │
│  Locked + 2:    已锁，有等待者              │
└──────────────────────────────────────────┘

锁定流程:
  1. CAS(0 → 1): 快速路径，无竞争
  2. 失败 → 自旋几次（spinlock）
  3. 失败 → futex(FUTEX_WAIT): 陷入内核等待
  4. 被唤醒 → 重新尝试 CAS

解锁流程:
  1. AtomicStore(0): 快速路径，无等待者
  2. 如果有等待者 → futex(FUTEX_WAKE): 唤醒一个
```

### RwLock 实现

`RwLock` 允许多个读者同时持有，但写者独占：

```text
┌─────────────────────────────────────────────┐
│              RwLock 内部状态                   │
│                                               │
│  写者计数: Writer Count (独占锁)              │
│  读者计数: Reader Count (共享锁)              │
│                                               │
│  lock():                                      │
│    读模式: Reader Count += 1                  │
│    写模式: CAS(0 → 1), 等待所有读者释放        │
│                                               │
│  读者-写者公平策略:                             │
│    不公平: 写者可能饥饿（更多吞吐量）           │
│    公平:   写者优先（降低延迟但降低吞吐量）      │
└─────────────────────────────────────────────┘
```

### Arc<Mutex<T>> 模式详解

这是 Rust 多线程共享可变状态的惯用模式：

```rust
use std::sync::{Arc, Mutex};
use std::thread;

// Arc (Atomic Reference Count) — 线程安全的引用计数
// Mutex<T> — 互斥锁保护内部数据

let shared = Arc::new(Mutex::new(Vec::new()));

let mut handles = vec![];
for i in 0..10 {
    let shared = Arc::clone(&shared);  // Arc::clone 增加引用计数（原子操作）
    handles.push(thread::spawn(move || {
        let mut guard = shared.lock().unwrap();  // 获取 MutexGuard（RAII）
        guard.push(i);
        // MutexGuard 在作用域结束时自动 drop，释放锁
    }));
}

for h in handles { h.join().unwrap(); }

let data = shared.lock().unwrap();
assert_eq!(data.len(), 10);
```

### Mutex vs RwLock 性能对比

```text
场景分析:
┌──────────────────┬──────────────────┬──────────────────┐
│      场景         │   Mutex 性能      │  RwLock 性能     │
├──────────────────┼──────────────────┼──────────────────┤
│ 纯读 (99% 读)    │   中等            │  高              │
│ 纯写             │   高              │  低 (额外开销)    │
│ 读写混合 (50/50) │   中等            │  低              │
│ 短临界区          │   高              │  中等            │
│ 长临界区          │   低 (阻塞)       │  中等            │
└──────────────────┴──────────────────┴──────────────────┘

结论:
  - 读多写少 (>90% 读): RwLock 优
  - 写操作频繁: Mutex 优
  - 临界区极短: Mutex 优 (无 RwLock 内部原子操作开销)
  - 需要排序保证: Mutex 优 (RwLock 读锁之间无序)
```

## Send + Sync 深入解析

### 定义与语义

```text
Send:  拥有 T 的值可以安全地转移到另一个线程
Sync:  &T 可以安全地从另一个线程引用

关系：
  T: Send  ⇒  &T: Sync  （如果 T 可以跨线程转移，那么 &T 可以跨线程引用）
  T: Sync  ⇒  &T: Send  （反过来也成立）

不是所有类型都是 Send/Sync:
  - Rc<T>: !Send (非原子引用计数)
  - Rc<T>: !Sync (非原子引用计数)
  - Cell<T>: !Sync (内部可变性但非线程安全)
  - RefCell<T>: !Sync (同上)
```

### 自动派生规则

```text
如果 T 的所有字段都是 Send，则 T 自动实现 Send
如果 T 的所有字段都是 Sync，则 T 自动实现 Sync

典型例子:
  Arc<T>:  Send (原子引用计数，线程安全)
  Arc<T>:  Sync (如果 T: Send + Sync)
  Mutex<T>: Send (锁保护)
  Mutex<T>: Sync (如果 T: Send)  ← 注意：T 只需 Send 不需 Sync
  RwLock<T>: Send + Sync (如果 T: Send + Sync)
```

### 手动实现 Send/Sync

```rust
use std::marker::PhantomData;
use std::rc::Rc;

// Rc<T> 不是 Send，我们不能绕过这个限制
// 但可以为包装类型手动实现 unsafe impl

struct MyWrapper<T> {
    inner: Rc<T>,
}

// 这是 unsafe 的，因为 Rc<T> 的引用计数不是原子的
// 如果真的跨线程使用，会导致数据竞争
// unsafe impl<T: Send> Send for MyWrapper<T> {}
// ← 这是危险的，仅用于教学目的

// 安全的做法：使用 Arc<T> 替代
struct SafeWrapper<T> {
    inner: std::sync::Arc<T>,
}
// Arc<T> 自动实现 Send + Sync
```

### PhantomData 与 Send/Sync

```rust
use std::marker::PhantomData;

// PhantomData<T> 声明"逻辑上"拥有 T，但不实际存储
// 编译器用它来推导 Send/Sync

struct MyType {
    _marker: PhantomData<*const ()>,  // *const () 不是 Send/Sync
}

// 通过 PhantomData<*const ()>，MyType 变为 !Send + !Sync
// 这在 FFI 场景中有用：某些 C 库的指针不能跨线程使用
```

## 与 C pthreads 的对比

### API 层面

```c
// C pthreads
#include <pthread.h>

pthread_mutex_t mutex = PTHREAD_MUTEX_INITIALIZER;

void* worker(void* arg) {
    pthread_mutex_lock(&mutex);
    // 临界区
    pthread_mutex_unlock(&mutex);
    return NULL;
}

int main() {
    pthread_t threads[10];
    for (int i = 0; i < 10; i++) {
        pthread_create(&threads[i], NULL, worker, NULL);
    }
    for (int i = 0; i < 10; i++) {
        pthread_join(threads[i], NULL);
    }
}
```

```rust
// Rust equivalent
use std::sync::{Arc, Mutex};
use std::thread;

fn main() {
    let mutex = Arc::new(Mutex::new(0));
    let mut handles = vec![];

    for _ in 0..10 {
        let mutex = Arc::clone(&mutex);
        handles.push(thread::spawn(move || {
            let mut guard = mutex.lock().unwrap();
            // 临界区
            // MutexGuard 自动 drop 解锁 — 不可能忘记！
        }));
    }

    for h in handles { h.join().unwrap(); }
}
```

### 安全性对比

```text
┌─────────────────────┬──────────────────┬──────────────────┐
│       特性           │   C pthreads     │   Rust std       │
├─────────────────────┼──────────────────┼──────────────────┤
│ 忘记解锁             │   可能死锁        │   编译错误        │
│ 数据竞争             │   运行时才发现     │   编译时阻止      │
│ 悬垂引用             │   可能发生        │   编译时阻止      │
│ 类型安全             │   void*          │   泛型类型系统     │
│ 锁释放保证           │   依赖程序员      │   RAII 自动保证   │
│ 原子操作类型安全      │   宏             │   类型安全的 API  │
│ 死锁检测             │   需要工具        │   代码审查 + 设计 │
└─────────────────────┴──────────────────┴──────────────────┘
```

### RAII 锁管理

```rust
use std::sync::Mutex;

fn example() {
    let m = Mutex::new(42);

    {
        let guard = m.lock().unwrap();
        // 使用 *guard 操作数据
        // 无论此作用域如何退出（正常/panic），
        // MutexGuard 都会 drop，释放锁
    }
    // 锁已释放

    // lock() 在 panic 时会返回 PoisonError
    // 可以用 .unwrap_or_else(|e| e.into_inner()) 恢复
    let val = m.lock().unwrap_or_else(|poisoned| {
        poisoned.into_inner() // 即使被毒化也获取值
    });
}
```

## 数据竞争 vs 竞态条件

### 数据竞争（Data Race）

```text
定义：两个线程同时访问同一内存地址，至少一个是写入，且没有同步机制。

三个条件同时满足时发生数据竞争：
  1. 至少两个线程访问同一内存地址
  2. 至少一个线程是写入
  3. 没有同步机制（Mutex, Atomic, Channel 等）

Rust 编译器在编译时阻止数据竞争！
  - 所有权系统确保同一时刻只有一个可变引用
  - Send/Sync 确保共享状态只能被安全访问
```

### 竞态条件（Race Condition）

```text
定义：程序输出依赖于线程的执行顺序。

竞态条件 ≠ 数据竞争

竞态条件可能在安全代码中发生：
  - 两个线程同时检查条件并执行操作
  - 条件在检查和执行之间可能改变

示例：TOCTOU (Time of Check to Time of Use)
```

```rust
use std::sync::{Arc, Mutex};
use std::thread;

let balance = Arc::new(Mutex::new(1000));

// 竞态条件：即使没有数据竞争，逻辑仍然错误
// 两个线程同时检查余额，都认为足够，然后同时扣款
for _ in 0..2 {
    let balance = Arc::clone(&balance);
    thread::spawn(move || {
        let b = balance.lock().unwrap();
        if *b >= 500 {
            // 两个线程都可能进入这里
            drop(b); // 释放锁
            let mut b = balance.lock().unwrap();
            *b -= 500; // 结果可能是 0 而不是预期的 500
        }
    });
}

// 解决方案：在检查和操作之间持有锁
```

## 高级并发模式

### Channel 模式

```rust
use std::sync::mpsc;
use std::thread;

// mpsc: Multiple Producer, Single Consumer
let (tx, rx) = mpsc::channel();

// 多个生产者
for i in 0..5 {
    let tx = tx.clone();
    thread::spawn(move || {
        tx.send(i).unwrap();
    });
}
drop(tx); // 重要：关闭原始发送端

// 消费者
while let Ok(val) = rx.recv() {
    println!("received: {}", val);
}
```

### scoped threads（线程作用域）

```rust
use std::thread;

let mut data = vec![1, 2, 3, 4, 5];

// scoped threads 可以借用局部变量
// 因为保证 join 在作用域结束前完成
thread::scope(|s| {
    let half = &mut data[0..2];
    let other_half = &mut data[2..];

    s.spawn(|| {
        for x in half.iter_mut() { *x *= 2; }
    });
    s.spawn(|| {
        for x in other_half.iter_mut() { *x *= 3; }
    });
}); // 两个线程在此自动 join

println!("{:?}", data); // [2, 4, 9, 12, 15]
```

### Once — 一次性初始化

```rust
use std::sync::Once;
use std::sync::OnceLock;

static INIT: Once = Once::new();
static mut VALUE: Option<String> = None;

// 线程安全的一次性初始化
fn get_value() -> &'static str {
    unsafe {
        INIT.call_once(|| {
            VALUE = Some(String::from("initialized"));
        });
        VALUE.as_ref().unwrap()
    }
}

// 更好的方式：使用 OnceLock（Rust 1.70+）
static VALUE: OnceLock<String> = OnceLock::new();

fn get_value_safe() -> &'static str {
    VALUE.get_or_init(|| String::from("initialized"))
}
```

## 调试并发问题

### 死锁检测

```text
死锁的四个必要条件（Coffman 条件）：
  1. 互斥（Mutual Exclusion）
  2. 持有并等待（Hold and Wait）
  3. 不可剥夺（No Preemption）
  4. 循环等待（Circular Wait）

预防策略：
  - 固定锁的获取顺序（消除循环等待）
  - 尽量减少锁的持有时间
  - 使用 try_lock 避免阻塞
  - 使用 Rust 的所有权系统消除数据竞争
```

## 语法

```rust
use std::thread;
use std::sync::{Arc, Mutex};
use std::sync::atomic::{AtomicI32, Ordering};

// 基础线程
let handle = thread::spawn(|| { println!("worker"); });
handle.join().unwrap();

// Arc + Mutex — 多线程共享可变状态
let counter = Arc::new(Mutex::new(0));
let mut handles = vec![];
for _ in 0..10 {
 let c = Arc::clone(&counter);
 handles.push(thread::spawn(move || {
 let mut n = c.lock().unwrap();
 *n += 1;
 }));
}
for h in handles { h.join().unwrap(); }

// 原子类型
let a = AtomicI32::new(0);
a.fetch_add(1, Ordering::SeqCst);

// mpsc 通道
use std::sync::mpsc;
let (tx, rx) = mpsc::channel();
thread::spawn(move || { tx.send(42).unwrap(); });
assert_eq!(rx.recv().unwrap(), 42);
```

### 内存序层级

| Ordering | 保证 | 性能 |
|----------|------|------|
| `Relaxed` | 原子性，重排随意 | 最快 |
| `Acquire/Release` | 成对同步，单方向屏障 | 中等 |
| `AcqRel` | 双向屏障 | 慢 |
| `SeqCst` | 全局顺序一致性 | 最慢 |
