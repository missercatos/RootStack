# 编译器如何理解你的代码

## 原理

Rust 编译器工作流程：

```
源码 (.rs)
 → Lexer/Parse → AST (abstract syntax tree)
 → HIR (high-level IR): 宏展开后、类型推导前的 IR
 → MIR (mid-level IR): 控制流图形式，borrow check、drop elaboration、优化
 → LLVM IR: SSA 形式的底层表示
 → 目标平台机器码
```

**HIR** 阶段：AST → 高层表示，保留 Rust 语义。用于类型推导和 trait 解析。

**MIR** 阶段（关键）：将 HIR 降级为控制流图。这是 borrow checker、NLL（non-lexical lifetimes）分析、drop 插入、常量求值的舞台。MIR 是 Rust 安全保证的核心编译阶段。

**LLVM IR** 阶段：MIR → LLVM IR。LLVM 执行优化 pass（内联、循环展开、noalias 利用、SIMD 向量化等）。`-C opt-level=3` 控制优化力度。

rust-analyzer 使用 libsyntax2 提供 IDE 级别的实时分析（不完整编译，仅增量分析）。

Cargo 的增量编译：MIR 单元按函数粒度缓存，只重编译有变化的函数。Clean build vs incremental：增量编译在 10%~50% 的时间完成。

## HIR → MIR → LLVM IR 完整管线

### 第一阶段：词法分析与语法分析

```text
源码 → Token 流 → AST

源码: fn main() { let x = 1 + 2; }

Token 流:
  [Fn] [Ident("main")] [LParen] [RParen] [LBrace]
  [Let] [Ident("x")] [Eq] [IntLit(1)] [Plus] [IntLit(2)] [Semi]
  [RBrace]

AST (简化):
  Item(Fn) {
    name: "main",
    body: Block {
      stmts: [
        Let(Pat::Ident("x"), Expr::BinOp(Plus, Lit(1), Lit(2)))
      ]
    }
  }
```

### 第二阶段：宏展开与 HIR 生成

```text
AST → 宏展开 → HIR

宏展开:
  vec![1, 2, 3] → { let mut v = Vec::new(); v.push(1); v.push(2); v.push(3); v }

HIR 与 AST 的区别:
  - HIR 已展开宏
  - HIR 已解析类型（部分）
  - HIR 包含 desugaring（语法糖展开）
    - for loop → loop + Iterator::next
    - if let → match
    - async fn → fn 返回 impl Future
    - ? → match + return
```

### 第三阶段：MIR 降级（核心）

```text
HIR → MIR

MIR 是控制流图（CFG）形式：

fn main() -> i32 {
    let x: i32;
    let _temp: i32;

    bb0: {
        _temp = Add(1, 2);   // 基本块 0
        x = _temp;
        return;
    }
}

MIR 的关键特性:
  - 每个函数是一个控制流图
  - 每个基本块（basic block）包含一系列语句
  - 最后一个语句是终止符（terminator）
  - 变量有明确的类型
  - 所有隐式操作显式化
```

### 第四阶段：LLVM IR 生成

```text
MIR → LLVM IR

LLVM IR (简化):
  define i32 @main() {
  entry:
    %x = add i32 1, 2
    ret i32 %x
  }

LLVM IR 的特点:
  - SSA (Static Single Assignment) 形式
  - 每个变量只赋值一次
  - 平台无关的中间表示
  - 支持丰富的优化 pass
```

### 第五阶段：机器码生成

```text
LLVM IR → 优化 → 汇编 → 机器码 → 目标文件

x86_64 汇编 (优化后):
  main:
      mov     eax, 3      ; 1 + 2 = 3，编译器常量折叠
      ret

注意：优化后 x 被完全消除（死代码消除）
```

## MIR 详解

### MIR 的结构

```text
MIR 函数结构:

fn example(x: i32) -> i32 {
    // 局部变量声明
    let mut _0: i32;          // 返回值
    let _1: i32;              // 参数 x
    let _2: i32;              // 临时变量

    // 基本块
    bb0: {
        _2 = Add(_1, 1);      // 语句
        _0 = _2;              // 赋值给返回值
        return;               // 终止符
    }
}

关键概念:
  - 每个基本块（bb）有 0 或多个语句 + 1 个终止符
  - 终止符类型: Goto, SwitchInt, Return, UnwindResume, etc.
  - 所有变量在使用前必须定义（SSA-like）
```

### Borrow Check 在 MIR 中的位置

```text
编译流程中的 borrow check:

HIR
  │
  ▼
MIR 生成
  │
  ▼
MIR 基本结构
  │
  ▼
┌─────────────────────────┐
│    Borrow Checker (NLL)  │ ← 在这里检查！
│    - 生命周期推导         │
│    - 借用规则检查         │
│    - 移动语义检查         │
└─────────────────────────┘
  │
  ▼
Drop Elaboration
  │
  ▼
MIR 优化
  │
  ▼
LLVM IR 生成
```

**为什么 borrow check 在 MIR 层而非 LLVM IR 层？**

```text
原因:
  1. MIR 保留了 Rust 语义（所有权、借用、生命周期）
  2. LLVM IR 已丢失这些语义信息
  3. MIR 是控制流图，便于分析跨基本块的生命周期
  4. NLL (Non-Lexical Lifetimes) 需要 MIR 的 CFG 结构

示例 — NLL 如何工作:

fn example() {
    let mut x = 5;
    let y = &x;        // y 的生命周期开始
    println!("{}", y);
    // y 不再使用，生命周期结束
    x += 1;            // 安全：y 已失效
}
```

### Drop Elaboration

```text
MIR 中的 drop 插入:

源码:
  let x = String::from("hello");
  let y = x;
  // x 的值已移动，但编译器仍需在 panic 路径上 drop x

MIR (简化):
  bb0: {
      x = String::new("hello");
      y = x;                    // 移动
      goto -> bb1;
  }
  bb1: {
      use(y);
      return;
  }
  // panic 路径:
  bb2: {                         // cleanup block
      drop(x);                   // 如果在 bb0-bb1 间 panic，drop x
      resume;
  }

Drop Elaboration 的职责:
  - 确定每个变量在哪些控制流路径上需要 drop
  - 插入 drop 调用
  - 处理 panic 路径的 cleanup
```

## LLVM 优化 Pass 详解

### 主要优化 pass

```text
LLVM 优化管线 (简化):

源 → [简化] → [内联] → [循环优化] → [向量化] → [死代码消除] → 优化后

常用优化:
┌──────────────────────┬─────────────────────────────────────┐
│ 优化名称              │ 作用                                │
├──────────────────────┼─────────────────────────────────────┤
│ -mem2reg             │ 将内存操作提升为寄存器（SSA 构建）    │
│ -simplifycfg         │ 简化控制流图（合并基本块）            │
│ -instcombine         │ 指令合并（a + 0 → a）               │
│ -gvn                 │ 全局值编号（消除冗余计算）            │
│ -loop-unroll         │ 循环展开                            │
│ -loop-vectorize      │ 循环向量化（SIMD）                   │
│ -slp-vectorize       │ SLP 向量化                          │
│ -inline              │ 函数内联                            │
│ -dce                 │ 死代码消除                          │
│ -dead-store-elim     │ 死存储消除                          │
│ -licm                │ 循环不变量外提                      │
└──────────────────────┴─────────────────────────────────────┘
```

### noalias 优化

```rust
fn add(x: &mut i32, y: &mut i32) {
    *x += 1;
    *y += 1;
    *x += 1;
}

// LLVM IR (优化前):
//   %x = load i32, ptr %x_ptr
//   %x1 = add i32 %x, 1
//   store i32 %x1, ptr %x_ptr
//   %y = load i32, ptr %y_ptr
//   %y1 = add i32 %y, 1
//   store i32 %y1, ptr %y_ptr
//   %x2 = load i32, ptr %x_ptr
//   %x3 = add i32 %x2, 1
//   store i32 %x3, ptr %x_ptr

// LLVM 优化后（因为 noalias，x 和 y 不可能指向同一地址）:
//   %x = load i32, ptr %x_ptr
//   %y = load i32, ptr %y_ptr
//   %x_new = add i32 %x, 2    ← 两次 x+=1 合并
//   %y_new = add i32 %y, 1
//   store i32 %x_new, ptr %x_ptr
//   store i32 %y_new, ptr %y_ptr
```

### 常量折叠与传播

```rust
const fn fibonacci(n: u32) -> u32 {
    match n {
        0 => 0,
        1 => 1,
        _ => fibonacci(n - 1) + fibonacci(n - 2),
    }
}

let x = fibonacci(10);
// 编译时计算: x = 55
// 生成的代码: mov eax, 55
```

## 编译速度优化

### 影响编译速度的因素

```text
编译时间分解:
  1. 编译依赖 (cargo build -p <dep>)
     - 首次编译最慢
     - 增量编译时通常不变

  2. 宏展开
     - 过程宏显著增加编译时间
     - 声明宏影响较小

  3. 类型推导与 trait 解析
     - 泛型越多，trait 解析越慢
     - 复杂的 trait bound 增加编译时间

  4. Borrow Check
     - NLL 分析可能很慢（复杂生命周期）

  5. 代码生成（LLVM）
     - 泛型单态化生成大量代码
     - 优化级别影响很大

  6. 链接
     - debug 链接较快
     - release + LTO 链接很慢
```

### 优化技巧

```text
1. 使用 cargo check 替代 cargo build
   - 只运行到 borrow check 阶段
   - 跳过代码生成和链接
   - 快 3-5 倍

2. 减少泛型单态化
   - 使用 trait object (Box<dyn Trait>) 替代泛型
   - 减少编译器生成的代码量

3. 使用 sccache
   - 缓存编译结果
   - 跨项目共享缓存

4. 使用 mold 链接器（Linux）
   - 比 lld 快 3-5 倍
   - cargo install mold
   - RUSTFLAGS="-C link-arg=-fuse-ld=mold" cargo build

5. 使用 ThinLTO
   - 比 fat LTO 快得多
   - -C lto=thin

6. 拆分 crate
   - 大 crate 编译慢
   - 拆分为多个小 crate
   - 利用增量编译
```

### 编译时间分析

```bash
# 分析编译时间
cargo build --timings

# 详细时间分析
cargo build -Z time-passes

# 查看代码生成时间
cargo build -Z time-passes 2>&1 | grep codegen
```

## ThinLTO vs Full LTO

### Full LTO

```text
Full LTO:
  1. 合并所有 crate 的 LLVM IR 为单一模块
  2. 对整个程序进行优化
  3. 最佳优化效果
  4. 编译时间长，内存占用大

  所有 .rlib → 合并为单一 LLVM 模块 → 优化 → 生成
```

### ThinLTO

```text
ThinLTO:
  1. 保留每个 crate 的 LLVM IR
  2. 使用摘要（summary）进行跨 crate 优化
  3. 支持并行编译
  4. 编译时间接近无 LTO
  5. 优化效果略差于 Full LTO

  .rlib → 保留独立 LLVM 模块 + 摘要 → 并行优化 → 链接
```

### 增量编译与 LTO

```text
增量编译时 LTO 的处理:

  - ThinLTO: 只重新编译变化的模块，保留缓存的摘要
  - Full LTO: 整个程序重新合并和优化（增量效果差）

  建议:
    - 开发时: 不使用 LTO (-C lto=off)
    - CI: 使用 ThinLTO (-C lto=thin)
    - 发布: 使用 Full LTO (-C lto=fat)
```

| 标志 | 作用 |
|------|------|

| `-C debuginfo=0..2` | 调试信息 |
| `-C lto=fat/thin` | 链接时优化 |
