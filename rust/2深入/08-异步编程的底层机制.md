# 异步编程的底层机制

## 原理

Rust 异步运行时基于协作式调度（cooperative scheduling）。`async fn` 在编译时被转换为实现了 `Future` trait 的状态机——每个 `.await` 点对应状态机的一个状态。

`Future` trait 的 `poll(self: Pin<&mut Self>, cx: &mut Context) -> Poll<Self::Output>` 方法被 executor 调用。Future 返回 `Poll::Pending` 表示未就绪，并通过 `cx.waker().wake()` 注册回调；返回 `Poll::Ready(v)` 表示完成。

`Pin` 保证 Future 在内存中不移动（自引用结构体的安全要求）。编译器生成的匿名类型包含所有跨 `.await` 的局部变量。

Executor（如 tokio）内部维护就绪队列和 IO 事件循环（epoll/io_uring）。`tokio::spawn` 将 Future 提交到线程池的任务队列中。

与 OS 线程对比：异步 Task 切换无内核参与（用户态切换），单个线程可管理数万个并发连接（C10K/C100K 问题解决）。

## Future trait 状态机深度解析

### async fn 的编译期展开

当你编写 `async fn` 时，编译器将其转换为一个实现了 `Future` trait 的匿名 `enum`。每个 `.await` 点对应枚举的一个变体（variant）。

```text
源码：
async fn example(x: i32) -> i32 {
    let a = do_a(x).await;
    let b = do_b(a).await;
    b + 1
}

编译器内部转换（概念性）：
enum ExampleFuture {
    // 状态 0: 初始状态，等待 do_a
    State0 { x: i32, do_a_future: DoAFuture },
    // 状态 1: do_a 完成，等待 do_b
    State1 { a: i32, do_b_future: DoBFuture },
    // 状态 2: 完成
    Complete,
}

impl Future for ExampleFuture {
    type Output = i32;

    fn poll(self: Pin<&mut Self>, cx: &mut Context) -> Poll<i32> {
        loop {
            match self {
                State0 { x, do_a_future } => {
                    match do_a_future.poll(cx) {
                        Poll::Ready(a) => {
                            // 转换到状态 1
                            *self = State1 { a, do_b_future: do_b(a) };
                            continue; // 立即轮询下一个
                        }
                        Poll::Pending => return Poll::Pending,
                    }
                }
                State1 { a, do_b_future } => {
                    match do_b_future.poll(cx) {
                        Poll::Ready(b) => {
                            return Poll::Ready(b + 1);
                        }
                        Poll::Pending => return Poll::Pending,
                    }
                }
                Complete => panic!("polled after completion"),
            }
        }
    }
}
```

### 状态机内存布局

```text
sizeof(ExampleFuture) = max(sizeof(State0), sizeof(State1))

关键：跨 .await 的变量被存储在状态机中
      只在 .await 之间存在的变量可以被优化掉

struct ExampleFuture {
    // discriminant (tag) — 标识当前状态
    tag: u8,
    // padding for alignment
    _padding: [u8; 7],
    // 状态 0 的数据
    union {
        state0: { x: i32, do_a_future: DoAFuture },
        state1: { a: i32, do_b_future: DoBFuture },
    },
}

所有状态共用同一块内存 — 这就是为什么 async fn 比手写 Future 更高效
```

### Waker 机制详解

`Waker` 是 Future 和 Executor 之间的桥梁：

```text
┌─────────────────────────────────────────────────────┐
│                  Executor (tokio)                    │
│                                                      │
│  1. 从就绪队列取出任务                                │
│  2. 调用 future.poll(cx)                             │
│  3. 如果返回 Pending:                                │
│     - Future 已通过 cx.waker().wake() 注册回调       │
│     - 任务返回就绪队列                                │
│  4. 如果返回 Ready:                                  │
│     - 任务完成，drop future                          │
│                                                      │
│  当 IO 事件就绪时:                                    │
│     - epoll/io_uring 通知 Waker                      │
│     - Waker 将任务放入就绪队列                         │
│     - Executor 下次循环会重新 poll 该 Future           │
└─────────────────────────────────────────────────────┘
```

```rust
use std::future::Future;
use std::pin::Pin;
use std::task::{Context, Poll};
use std::time::{Duration, Instant};

// 手动实现 Future — 理解底层机制
struct Delay {
    when: Instant,
}

impl Future for Delay {
    type Output = ();

    fn poll(self: Pin<&mut Self>, cx: &mut Context) -> Poll<()> {
        if Instant::now() >= self.when {
            Poll::Ready(())
        } else {
            // 注册 waker，稍后会被再次调度
            let waker = cx.waker().clone();
            let when = self.when;
            std::thread::spawn(move || {
                let remaining = when - Instant::now();
                std::thread::sleep(remaining);
                waker.wake(); // 通知 executor 重新 poll
            });
            Poll::Pending
        }
    }
}
```

## Pin\<T\> 深度解析

### 为什么需要 Pin

当 Future 生成的状态机包含**自引用**（self-referential）时，移动它会导致悬垂指针。

```text
问题场景：

async fn example() {
    let data = vec![1, 2, 3];
    let reference = &data; // reference 引用 data
    some_async_op().await;  // 此后 data 和 reference 一起存储在状态机中
    println!("{:?}", reference);
}

状态机 State1 包含:
  - data: Vec<i32>     (堆上分配)
  - reference: &[i32]  (指向 data 的内部指针)

如果状态机被移动到新内存地址:
  - data 被复制/移动到新地址
  - reference 仍指向旧地址 ← 悬垂指针！
```

### Pin 的保证

```text
Pin<&mut T> 保证：
  1. T 在内存中不会被移动（move）
  2. T 不会被 drop 后重用（no-overwrite）

Pin 的实现：
  Pin<Ptr> 本质上是一个包装了指针的 newtype
  它在编译期强制执行 "no-move" 约束

  struct Pin<Ptr> {
      pointer: Ptr,  // 只是普通指针包装
  }

  // 但 unsafe 代码中，你可以：
  // unsafe { Pin::get_unchecked_mut(&mut pin) }  — 获取可变引用
  // 但这违反了 Pin 的不变量，可能导致 UB
```

### Pin 的 API

```rust
use std::future::Future;
use std::pin::Pin;
use std::task::{Context, Poll};

// 创建 pinned future
let future = async { 42 };
let mut pinned: Pin<&mut dyn Future<Output = i32>> = Box::pin(future);

// poll pinned future
let mut cx = /* ... */;
match pinned.as_mut().poll(&mut cx) {
    Poll::Ready(val) => println!("{}", val),
    Poll::Pending => println!("not ready"),
}

// Pin::new — 用于 Unpin 类型
// Unpin 表示 "移动不会造成问题"（大多数类型都是 Unpin）
let mut x = 42;
let mut pinned = Pin::new(&mut x);
// 对 Unpin 类型，Pin 没有实际约束

// pin! 宏（Rust 1.68+）— 在栈上创建 pinned 值
use std::pin::pin;
let future = pin!(async { 42 });
// future 是 Pin<&mut SomeFuture>，不能被移动
```

### Unpin trait

```text
Unpin: 标记类型可以安全移动（即使被 Pin 包装）

自动实现：
  - 所有基本类型 (i32, String, Vec<T>, ...) 都是 Unpin
  - 大多数用户定义类型也是 Unpin

手动 opt-out：
  - struct MyFuture { ... }
  - impl !Unpin for MyFuture {}  // 声明 "移动不安全"

  async fn 生成的类型默认 !Unpin（因为可能包含自引用）
```

### 编译器的完整变换

```text
源码：
async fn fetch_url(url: &str) -> Result<String, Error> {
    let resp = reqwest::get(url).await?;

}

impl<'a> Future for FetchUrlFuture<'a> {
    type Output = Result<String, Error>;

    fn poll(self: Pin<&mut Self>, cx: &mut Context) -> Poll<Self::Output> {
        // 根据当前状态分派
        // 每个 .await 点生成一个 match 分支
    }
}
```

### .await 的展开

```text
// 编译器将 .await 展开为：

loop {
    match <future as Future>::poll(Pin::new(&mut future), cx) {
        Poll::Ready(value) => break value,
        Poll::Pending => {
            // 保存当前上下文
            // 返回 Poll::Pending 给调用者
            return Poll::Pending;
        }
    }
}
// 注意：loop 确保在 waker wake 后立即重新 poll
```

## tokio 运行时架构

### 工作窃取（Work-Stealing）

```text
┌─────────────────────────────────────────────────┐
│              tokio Runtime                       │
│                                                  │
│  ┌──────────┐ ┌──────────┐ ┌──────────┐         │
│  │ Thread 1  │ │ Thread 2  │ │ Thread 3  │         │
│  │ 本地队列  │ │ 本地队列  │ │ 本地队列  │         │
│  │ [T1,T2]  │ │ [T3]     │ │ [T4,T5]  │         │
│  └────┬─────┘ └────┬─────┘ └────┬─────┘         │
│       │             │             │                │
│       └───── 全局队列 ◄──────────┘                │
│              [T6, T7, ...]                        │
│                                                  │
│  工作窃取: Thread 1 队列空时，                     │
│           从 Thread 2/3 的队列尾部窃取任务          │
└─────────────────────────────────────────────────┘

工作窃取算法:
  1. 优先从本地队列取任务
  2. 本地队列空 → 从全局队列取
  3. 全局队列空 → 从其他线程的本地队列窃取（尾部）
  4. 所有队列空 → 线程休眠（park）

优势:
  - 减少锁竞争（本地队列无锁）
  - 负载均衡（自动分配任务）
  - 缓存友好（任务倾向于在同一 CPU 执行）
```

### IO 驱动

```text
┌─────────────────────────────────────────────────┐
│              tokio IO Driver                     │
│                                                  │
│  Linux: epoll                                    │
│    ┌─────────────────────────────┐              │
│    │ epoll_wait() 阻塞等待       │              │
│    │ 返回就绪的 fd               │              │
│    │ → 唤醒对应的 Waker          │              │
│    └─────────────────────────────┘              │
│                                                  │
│  Linux 5.1+: io_uring                            │
│    ┌─────────────────────────────┐              │
│    │ 提交队列 (SQ) → 内核        │              │
│    │ 完成队列 (CQ) ← 内核        │              │
│    │ 零拷贝，减少系统调用         │              │
│    └─────────────────────────────┘              │
│                                                  │
│  macOS: kqueue                                   │
│  Windows: IOCP                                   │
└─────────────────────────────────────────────────┘
```

### epoll vs io_uring

```text
┌──────────────────┬──────────────────┬──────────────────┐
│       特性        │     epoll        │    io_uring      │
├──────────────────┼──────────────────┼──────────────────┤
│ 系统调用次数       │ 每次 IO 需要     │ 批量提交/完成     │
│ 零拷贝            │ 不支持            │ 支持              │
│ 异步文件 IO       │ 不支持            │ 支持              │
│ 内存共享          │ 不支持            │ 共享环形缓冲区    │
│ 性能 (10K 连接)   │ 高                │ 更高              │
│ 内核版本要求       │ 2.6+             │ 5.1+              │
└──────────────────┴──────────────────┴──────────────────┘

io_uring 工作原理:
  ┌──────────────────┐
  │   用户空间        │
  │  提交队列 (SQE)  │ ──────► ┌──────────┐
  │                   │         │   内核    │
  │  完成队列 (CQE)  │ ◄────── │  处理 IO │
  └──────────────────┘         └──────────┘
  两个环形缓冲区共享内存，无需系统调用即可提交/获取结果
```

## 与其他语言的对比

### C++ Coroutines (C++20)

```text
C++20 Coroutines:
  - 编译器变换为状态机（类似 Rust）
  - 但没有 Pin 的保证（需要程序员保证自引用安全）
  - 没有内置的 executor（需要第三方库如 folly, Boost.Coroutine）
  - 无所有权系统（可能有悬挂引用）

对比：
  C++: co_await → 编译器生成 coroutine frame
  Rust: .await → 编译器生成 Future enum

  C++ 的 frame 可以被移动（危险！）
  Rust 的 Future 被 Pin 固定在内存中（安全）
```

### Go Goroutines

```text
Go Goroutines:
  - 用户态线程（M:N 调度）
  - 由 Go runtime 调度（抢占式调度）
  - 每个 goroutine 初始栈 2KB（可增长）
  - 通过 channel 进行通信（CSP 模型）

对比：
  Go: 抢占式调度，runtime 可以随时暂停 goroutine
  Rust: 协作式调度，Future 主动让出（.await）

  Go: 无 async/await 语法，直接写普通函数
  Rust: 需要 async fn 显式标记

  Go: 内置 GC，无需担心内存管理
  Rust: 无 GC，Pin 保证内存安全

  Go: 更简单，适合 IO 密集型
  Rust: 更底层，适合性能敏感场景
```

### JavaScript async/await

```text
JavaScript:
  - 单线程事件循环（Node.js）
  - Promise → async/await
  - 无 Pin 问题（值在闭包中被捕获）
  - 无编译期类型检查

Rust:
  - 多线程 executor
  - Future → async/await
  - Pin 保证自引用安全
  - 编译期零成本抽象

JS 的 Promise 创建就有开销（堆分配）
Rust 的 Future 是零成本的（编译为状态机）
```

## 高级 async 模式

### Stream（异步迭代器）

```rust
use tokio_stream::StreamExt;
use std::time::Duration;

// Stream: 异步产生一系列值
async fn process_stream() {
    let mut stream = tokio_stream::iter(vec![1, 2, 3, 4, 5]);

    while let Some(value) = stream.next().await {
        println!("processing: {}", value);
        tokio::time::sleep(Duration::from_millis(100)).await;
    }
}
```

### spawn_blocking — 桥接同步/异步

```rust
#[tokio::main]
async fn main() {
    // 将阻塞操作放到专用线程池
    let result = tokio::task::spawn_blocking(|| {
        // 这里可以安全地执行阻塞操作
        std::thread::sleep(Duration::from_secs(1));
        42
    }).await.unwrap();

    println!("result: {}", result);
}
```

### 结构化并发（JoinSet）

```rust
use tokio::task::JoinSet;

#[tokio::main]
async fn main() {
    let mut set = JoinSet::new();

    for i in 0..10 {
        set.spawn(async move {
            tokio::time::sleep(Duration::from_millis(100)).await;
            i * 2
        });
    }

    while let Some(result) = set.join_next().await {
        match result {
            Ok(val) => println!("completed: {}", val),
            Err(e) => eprintln!("task failed: {}", e),
        }
    }
}
```
