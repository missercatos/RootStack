# 所有权系统的计算机科学基础

## 原理

### 线性逻辑与仿射类型

Rust 所有权根植于**线性逻辑**（Linear Logic，由 Jean-Yves Girard 于 1987 年提出）中的 affine 类型理论。在线性逻辑中，命题是"资源"，恰好使用一次。Rust 将约束放宽为"最多一次"：每个非 Copy 值恰好被消耗（move）或销毁（drop）一次。

**名词解释**：

- **线性类型（Linear Type）**：该类型的值必须**恰好**被使用一次。不能被丢弃，也不能被多次使用。C++ 的 `std::unique_ptr` 近似于此（不能拷贝，只能移动一次）。
- **仿射类型（Affine Type）**：该类型的值**最多**被使用一次。可以被丢弃（相当于不使用），但不能被多次使用。Rust 的所有权系统基于此。
- **单调类型（Relevant Type）**：该类型的值**至少**被使用一次。不能被丢弃。
- **线性逻辑（Linear Logic）**：一种子结构逻辑，它限制了结构规则（弱化和收缩），使得每个前提必须恰好使用一次。

```text
类型系统资源使用规则对比:

线性类型 (Linear):    使用恰好 1 次   !x = 错误    x.x = 错误
仿射类型 (Affine):   使用最多 1 次   !x = OK      x.x = 错误
单调类型 (Relevant): 使用至少 1 次   !x = 错误    x.x = OK
普通类型 (Unrestricted): 使用任意次  !x = OK      x.x = OK

Rust 选择仿射类型的原因:
1. 必须允许丢弃 (函数返回时局部变量自动 drop)
2. 不允许多次使用 (防止 double-free 和 use-after-free)
3. Copy 类型是例外：它们的"拷贝"是按位复制，不违反仿射约束
```

### 形式化推导规则

Rust 所有权系统的形式化语义可以用类型推导规则表示：

```text
Move 语义的形式化推导规则:

  Γ ⊢ e₁ : T      Γ, x:T ⊢ e₂ : U
  ───────────────────────────────────  (let-move)
       Γ ⊢ let x = e₁; e₂ : U

  含义: 如果 e₁ 的类型为 T，且在扩展环境 (添加 x:T) 下 e₂ 的类型为 U，
       则 let x = e₁; e₂ 的类型为 U。
       关键: e₁ 被移动到 x，原变量在环境中被移除。

Copy 语义的形式化推导规则:

  Γ ⊢ e₁ : T  (T: Copy)      Γ, x:T ⊢ e₂ : U
  ───────────────────────────────────────────────  (let-copy)
       Γ ⊢ let x = e₁; e₂ : U

  含义: 如果 T 实现了 Copy，则 let 绑定不会移动 e₁，
       e₁ 在后续代码中仍可使用。

Drop 语义的形式化推导规则:

  Γ ⊢ e : T      Γ ⊢ drop(e) : ()
  ───────────────────────────────  (drop)
       Γ ⊢ { ... ; drop(e) } : U
```

### Move 语义在机器码层面

Move 语义在机器码层面仅为 `memcpy`（栈上 24B 的 ptr+len+cap），原变量位置被编译器标记为"已移动"，后续使用触发静态错误。编译器在 MIR（Mid-level Intermediate Representation）层面将 move 表示为"使用"，后续任何对该变量的访问都被视为使用已移动值。

```text
String 类型的 Move 过程 (机器码层面):

Before move:
  Stack:                Heap:
  ┌─────────────────┐   ┌──────────────────┐
  │ s1:              │   │ "hello"           │
  │   ptr ──────────┼──→│ h  e  l  l  o     │
  │   len = 5       │   └──────────────────┘
  │   cap = 5       │
  └─────────────────┘

After `let s2 = s1;` (memcpy 24 字节):
  Stack:                Heap:
  ┌─────────────────┐   ┌──────────────────┐
  │ s1: (无效)      │   │ "hello"           │
  │   ptr ─ ─ ─ ─ ─┼──→│ h  e  l  l  o     │
  │   len = ?       │   └──────────────────┘
  │   cap = ?       │        ↑ 引用计数不变
  ├─────────────────┤        │ (只有 Rc/Arc 有)
  │ s2:              │       │
  │   ptr ──────────┼───────┘
  │   len = 5       │
  │   cap = 5       │
  └─────────────────┘

编译器操作: 仅复制 24 字节 (ptr+len+cap)，不复制堆数据
后续访问 s1: 编译器在 MIR 中标记 s1 为 "moved"，编译时报错
```

### MIR Drop Elaboration

编译器确定 drop 位置的算法基于支配树：找到所有者不再存活的程序点（后支配边界），插入释放。

```text
MIR Drop Elaboration 过程:

原始 MIR (简化):
  bb0: {
      _1 = String::new();          // 创建 String
      _2 = _1;                     // move 到 _2
      _3 = _2;                     // move 到 _3
  }                                // _3 在此作用域结束时 drop

Drop Elaboration 后:
  bb0: {
      _1 = String::new();
      _2 = move _1;               // _1 标记为 moved
      _3 = move _2;               // _2 标记为 moved
      drop(_3) = [return: bb1, unwind: bb2]; // 显式插入 drop
  }

支配树分析:
  - 每个变量的 drop 位置 = 该变量所有使用点的最低公共支配者 (LCD)
  - 如果变量在所有路径上都被移动，drop 位置 = 移动点之后
  - 如果变量可能未被移动 (如条件分支)，需要在所有可能的出口点插入 drop

实际汇编:
  call    String::drop    ; 调用 T::drop
  mov     rdi, [rbp-24]   ; 取堆指针
  mov     rsi, [rbp-16]   ; 取布局大小
  call    __rust_dealloc  ; 释放堆内存
```

### 所有权规则总结

| 规则 | 说明 | 违反后果 |
|------|------|----------|
| 每个值有且仅有一个所有者 | 所有权的单一性 | 编译错误 |
| 所有权可以转移 (move) | 所有权的唯一转移 | 编译错误 |
| 所有者离开作用域时值被丢弃 (drop) | 自动资源管理 | 无 |
| 值可以被借用 (borrow) 但不转移所有权 | 共享/独占访问 | 编译错误 |

### 与 GC 语言的对比

| 语言 | 释放方式 | 运行时开销 | 双释放风险 | 内存泄漏风险 |
|------|----------|-----------|-----------|-------------|
| C | 手动 `free()` | 零 | 高 | 高 |
| C++ | RAII / `unique_ptr` | 零 | 中 | 中 |
| Java/Go | GC trace | 高 | 零 | 低 (循环引用) |
| Rust | 编译期 drop 插入 | 零 | 零 | 低 (Rc 循环) |

### 与 ML/OCaml 的比较

ML/OCaml 使用垃圾回收（GC）管理内存，不提供所有权系统。但 ML 的类型系统与 Rust 有相似之处：

```text
ML/OCaml vs Rust 类型系统对比:

ML/OCaml:
  - 函数式语言，不可变绑定是默认的
  - 可变引用: ref 类型 (本质上是堆上的单元素盒)
  - 内存管理: 追踪式 GC (mark-and-sweep)
  - 无所有权概念，值可以任意共享

Rust:
  - 系统语言，可变性是默认的
  - 可变引用: &mut T (编译期独占检查)
  - 内存管理: 所有权 + 借用检查 (零运行时开销)
  - 所有权系统防止数据竞争和悬垂引用

ML 的 "linear type" 实验:
  - Mezzo (2013): 研究语言，探索所有权和权限
  - Alms (2014): ML 扩展，添加线性类型
  - 这些研究影响了 Rust 的设计
```

## 语法

### 所有权转移的核心规则

```rust
let s1 = String::from("hello");
let s2 = s1; // move: s1 失效
// println!("{}", s1); // 编译错误

let x = 5;
let y = x; // Copy: x 仍有效
```

### Drop 与作用域

```rust
{
 let s = String::from("hi"); // s 获得所有权
 println!("{}", s); // s 使用中
} // s.drop() 在此插入

fn consume(s: String) { } // 参数接收所有权，结束时 drop
```

### 所有权图

$$
\text{所有者} \xrightarrow{\text{move}} \text{新所有者} \xrightarrow{\text{scope ends}} \text{drop}
$$

### 非词法生命周期（NLL）

```rust
let mut s = String::from("hi");
let r1 = &s;
println!("{}", r1); // r1 最后使用
let r2 = &mut s; // OK: r1 在此前已"死亡"（NLL）
```

### 深入理解所有权转移

```rust
// 所有权转移的实际场景

// 场景 1: 函数参数转移
fn process(data: String) {
    println!("{}", data);
} // data 在此 drop

let s = String::from("hello");
process(s);      // s 的所有权移动到函数参数 data
// println!("{}", s); // 错误: s 已被移动

// 场景 2: 返回值转移
fn create() -> String {
    let s = String::from("new");
    s // 所有权转移给调用者
}

let s = create(); // s 获得所有权

// 场景 3: 枚举变体中的所有权
enum Shape {
    Circle(f64),
    Rect(f64, f64),
    Text(String), // String 的所有权在 Shape 中
}

let shape = Shape::Text(String::from("hello"));
// shape 的所有者拥有内部 String 的所有权
// 当 shape drop 时，内部 String 也被 drop

// 场景 4: 结构体中的所有权
struct Person {
    name: String,
    age: u32,
}

let p = Person {
    name: String::from("Alice"),
    age: 30,
};

let name = p.name; // move: p.name 被移出
// println!("{}", p.name); // 错误: p.name 已被移动
// 但 p.age 仍然可用 (Copy 类型)
println!("{}", p.age); // OK: age 是 u32 (Copy)
```

### Copy 类型的特殊性

```rust
// Copy 类型在赋值时按位复制，不发生 move
// 所有 Copy 类型必须同时实现 Clone
// Copy 是自动 derive 的，但仅限于"简单"类型

#[derive(Copy, Clone)]
struct Point {
    x: i32,
    y: i32,
}

let p1 = Point { x: 1, y: 2 };
let p2 = p1; // Copy: p1 和 p2 都有效
println!("{:?} {:?}", p1, p2); // OK

// 以下类型不能实现 Copy:
// - 堆分配类型 (String, Vec<T>, Box<T>)
// - 包含非 Copy 字段的结构体
// - 实现了 Drop 的类型 (Copy 和 Drop 互斥)

// Copy 类型在汇编层面:
// mov eax, [rbp - 4]   ; 读取 p1.x
// mov [rbp - 8], eax   ; 写入 p2.x (完全相同的值)
// 没有任何额外操作，纯粹的内存复制
```

### 所有权与模式匹配

```rust
// 模式匹配可以转移所有权
enum Option<T> {
    Some(T),
    None,
}

let opt: Option<String> = Some(String::from("hello"));

match opt {
    Some(s) => {
        // s 获得 String 的所有权
        println!("{}", s);
    } // s 在此 drop
    None => {}
}

// opt 不能再使用 (已被 move 到 match 分支中)

// 如果需要保留所有权，使用 as_ref()
let opt: Option<String> = Some(String::from("hello"));
if let Some(s) = opt.as_ref() {
    println!("{}", s); // s 是 &String，不转移所有权
}
println!("{:?}", opt); // OK: opt 仍有效
```

## 深入理解

### 所有权系统的编译器实现

```text
Rust 编译器的借用检查流程:

1. HIR (High-level IR)
   └─→ 所有权规则检查 (HIR borrowck)
       └─→ 检查基本的所有权转移和借用规则

2. MIR (Mid-level IR)
   └─→ NLL borrowck (Non-Lexical Lifetimes)
       └─→ 基于控制流图的精确借用检查
       └─→ Drop elaboration (确定 drop 位置)
       └─→ 检查移动和借用的冲突

3. LLVM IR
   └─→ noalias 属性附加 (优化提示)
       └─→ LLVM 优化 pass 利用借用信息

借用检查的约束生成:
  每个借用生成一个约束:
    &x       → borrow(x, region)     // 共享借用
    &mut x   → borrow_mut(x, region) // 独占借用
    x        → consume(x)            // 移动/消费

  约束求解:
    - 共享借用: 不能与独占借用重叠
    - 独占借用: 不能与任何借用重叠
    - 移动: 必须在所有借用结束后发生
```

### 所有权与内存安全的等价性

```text
Rust 所有权系统保证的内存安全属性:

1. 无 use-after-free:
   所有权转移后，原变量失效
   编译器阻止访问已移动的值

2. 无 double-free:
   所有权转移后，原所有者的 drop 不会执行
   新所有者在作用域结束时 drop

3. 无数据竞争:
   &mut T 是独占的，编译期保证
   不可能同时有多个写入者

4. 无悬垂引用:
   引用的生命周期不能超过被引用数据
   编译器跟踪所有引用的生命周期

5. 无内存泄漏:
   所有分配都有对应的 drop (Rc 循环除外)
   作用域结束时自动释放
```

fn multiply(a: Vec<u32>, b: Vec<u32>) -> Vec<u32> {
 // a 和 b 的所有权移入，返回新 Vec
