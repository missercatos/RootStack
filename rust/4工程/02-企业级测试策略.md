# 企业级测试策略

## 企业场景

某在线支付平台在凌晨2:17遭遇了生产事故：并发退款请求导致用户账户余额被重复扣款，30分钟内损失$127,000。事故追溯发现，原有测试套件（2000+单元测试）全部通过，但并未覆盖到两个`tokio::spawn`之间的竞态条件。

安全审计要求：任何涉及资金操作的代码必须通过并发安全性测试、模糊测试和属性测试三层验证。此外，所有已修复的CVE必须配有回归测试，确保不会在版本迭代中重新引入。

## 1. 属性测试（Property-Based Testing）with proptest

传统单元测试验证"给定输入A，期望输出B"，只能覆盖程序员想到的用例。属性测试描述**不变性（invariant）**，由框架自动生成大量随机输入验证。

### 1.1 基本属性测试

```rust
use proptest::prelude::*;

/// 金额转移函数（被测对象）
/// 安全要求：转移后，两个账户的总额必须不变
fn transfer(from: &mut i64, to: &mut i64, amount: i64) -> Result<(), &'static str> {
    if amount <= 0 {
        return Err("金额必须为正数");
    }
    if *from < amount {
        return Err("余额不足");
    }
    // 故意的溢出漏洞：from - amount可能溢出
    *from -= amount;    // BUG: i64减法可能panic或溢出
    *to += amount;      // BUG: i64加法可能溢出
    Ok(())
}

proptest! {
    #[test]
    fn transfer_preserves_total(
        initial_from in -1_000_000i64..1_000_000i64,
        initial_to in -1_000_000i64..1_000_000i64,
        amount in 0i64..2_000_000i64,
    ) {
        let mut from = initial_from;
        let mut to = initial_to;
        let expected_total = from.checked_add(to);

        let result = transfer(&mut from, &mut to, amount);

        if let Ok(()) = result {
            let actual_total = from.checked_add(to);
            assert_eq!(expected_total, actual_total,
                "转移后总额应保持不变");
        } else {
            // 失败时状态应回滚（此处未实现回滚，测试会捕获）
            assert_eq!(from, initial_from, "失败时from应回滚");
            assert_eq!(to, initial_to, "失败时to应回滚");
        }
    }
}

// 运行：cargo test
// proptest默认运行256个随机用例，发现失败后会进行"收缩"找到最小反例：
// 例如: from = -9223372036854775808, amount = 1 → 溢出
```

### 1.2 安全属性的属性测试

```rust
use proptest::prelude::*;
use proptest::collection::vec;

/// 密码哈希验证系统
mod password_security {
    use argon2::{
        password_hash::{PasswordHasher, SaltString, PasswordVerifier},
        Argon2,
    };
    use rand::rngs::OsRng;

    pub fn hash_password(password: &[u8]) -> Result<String, argon2::password_hash::Error> {
        let salt = SaltString::generate(&mut OsRng);
        let argon2 = Argon2::default();
        Ok(argon2.hash_password(password, &salt)?.to_string())
    }

    pub fn verify_password(hash: &str, password: &[u8]) -> Result<bool, argon2::password_hash::Error> {
        let argon2 = Argon2::default();
        let parsed_hash = argon2::password_hash::PasswordHash::new(hash)?;
        Ok(argon2.verify_password(password, &parsed_hash).is_ok())
    }
}

proptest! {
    #[test]
    fn password_hash_is_deterministic(
        password in "[a-zA-Z0-9!@#$%]{8,64}"
    ) {
        // 属性1：相同密码的两次哈希应不同（因为有随机盐）
        let hash1 = password_security::hash_password(password.as_bytes()).unwrap();
        let hash2 = password_security::hash_password(password.as_bytes()).unwrap();
        assert_ne!(hash1, hash2, "相同密码应产生不同哈希（随机盐）");

        // 属性2：正确密码能通过验证
        assert!(password_security::verify_password(&hash1, password.as_bytes()).unwrap());

        // 属性3：错误密码不能通过验证
        let wrong = format!("{}!", password);
        assert!(!password_security::verify_password(&hash1, wrong.as_bytes()).unwrap());
    }

    #[test]
    fn base64_decode_encode_roundtrip(
        input in vec(any::<u8>(), 0..1024)
    ) {
        // 属性4：Base64编码/解码的往返恒等性
        use base64::Engine;
        let encoded = base64::engine::general_purpose::STANDARD.encode(&input);
        let decoded = base64::engine::general_purpose::STANDARD.decode(&encoded).unwrap();
        assert_eq!(input, decoded, "Base64往返应保持不变");
    }

    #[test]
    fn json_roundtrip_security(
        input in "[a-zA-Z0-9_ ]{0,200}"
    ) {
        // 属性5：JSON序列化不应注入意外字段
        let value = serde_json::json!({"data": input});
        let serialized = serde_json::to_string(&value).unwrap();
        let deserialized: serde_json::Value = serde_json::from_str(&serialized).unwrap();
        assert_eq!(value, deserialized, "JSON序列化/反序列化应幂等");

        // 安全属性：任何JSON输入不应导致panic
        let _: Result<serde_json::Value, _> = serde_json::from_str(&input);
    }
}
```

## 2. 模糊测试（Fuzzing）with cargo-fuzz

Fuzzing是一种通过生成大量随机/半随机输入来发现崩溃和未定义行为的自动化测试技术。对于Rust，即使安全代码不会产生内存错误，fuzzing仍能发现逻辑错误、panic和性能退化。

### 2.1 配置cargo-fuzz

### 2.2 编写Fuzz Target

```rust
// fuzz/fuzz_targets/parse_http_request.rs
#![no_main]

use libfuzzer_sys::fuzz_target;

/// 目标：HTTP请求解析器——常是攻击入口
/// 攻击向量：畸形HTTP头、超长URL、空字节注入
fuzz_target!(|data: &[u8]| {
    // 将任意字节传递给HTTP请求解析器
    if let Ok(request_str) = std::str::from_utf8(data) {
        // 测试1：解析不应panic
        let result = std::panic::catch_unwind(|| {
            parse_http_request(request_str)
        });

        if let Ok(parsed) = result {
            // 测试2：如果解析成功，输出不应包含原始敏感数据
            let output = format!("{:?}", parsed);
            assert!(!output.contains("Authorization:"),
                "调试输出不应包含Authorization头");

            // 测试3：如果解析成功，序列化回去应产生相同语义的结果
            // ... 属性断言
        }
    }
});

// 实际被测函数
#[derive(Debug)]
struct HttpRequest {
    method: String,
    path: String,
    headers: Vec<(String, String)>,
    body: Vec<u8>,
}

fn parse_http_request(raw: &str) -> Result<HttpRequest, String> {
    // 简化实现——实际应使用httparse等经过审计的库
    let mut lines = raw.lines();
    let first_line = lines.next().ok_or("空请求")?;
    let mut parts = first_line.split_whitespace();
    let method = parts.next().unwrap_or("GET").to_string();
    let path = parts.next().unwrap_or("/").to_string();

    // ⚠️ 安全：验证method是否为合法HTTP方法
    let valid_methods = ["GET", "POST", "PUT", "DELETE", "HEAD", "OPTIONS", "PATCH"];
    if !valid_methods.contains(&method.as_str()) {
        return Err(format!("非法HTTP方法: {}", method));
    }

    // ⚠️ 安全：限制path长度防止路径遍历
    if path.len() > 2048 {
        return Err("URL路径过长".to_string());
    }

    Ok(HttpRequest {
        method,
        path,
        headers: Vec::new(),
        body: Vec::new(),
    })
}
```

## 4. 并发测试：loom

`loom`是Tokio团队开发的并发测试框架，通过**穷举所有可能的线程交错**来发现竞态条件。

```rust
use loom::sync::atomic::{AtomicU64, Ordering};
use loom::thread;

#[test]
fn double_spend_detection_with_loom() {
    loom::model(|| {
        let balance = AtomicU64::new(100);
        let attempted_deduction = AtomicU64::new(0);

        let t1 = thread::spawn(|| {
            // 线程1：尝试扣款50
            let current = balance.load(Ordering::SeqCst);
            if current >= 50 {
                // ⚠️ TOCTOU漏洞：检查和扣款之间有窗口
                balance.store(current - 50, Ordering::SeqCst);
                attempted_deduction.fetch_add(50, Ordering::SeqCst);
            }
        });

        let t2 = thread::spawn(|| {
            // 线程2：尝试扣款70
            let current = balance.load(Ordering::SeqCst);
            if current >= 70 {
                balance.store(current - 70, Ordering::SeqCst);
                attempted_deduction.fetch_add(70, Ordering::SeqCst);
            }
        });

        t1.join().unwrap();
        t2.join().unwrap();

        let final_balance = balance.load(Ordering::SeqCst);
        let total_deducted = attempted_deduction.load(Ordering::SeqCst);

        // 关键安全断言：如果余额100，扣款总额不能超过100
        assert!(
            total_deducted <= 100,
            "双重扣款检测！余额100，但扣款{}", total_deducted
        );
    });
    // loom会尝试所有可能的线程交错执行顺序
    // 会检测到：T1读(100)→T2读(100)→T1写(50)→T2写(30)
    // 结果：余额30，但扣款120，断言失败！
}

// 🔧 正确实现：使用CAS（Compare-And-Swap）
#[test]
fn correct_double_spend_prevention() {
    loom::model(|| {
        let balance = AtomicU64::new(100);

        let deduct = |amount: u64| -> bool {
            loop {
                let current = balance.load(Ordering::SeqCst);
                if current < amount {
                    return false;
                }
                if balance
                    .compare_exchange(current, current - amount,
                        Ordering::SeqCst, Ordering::SeqCst)
                    .is_ok()
                {
                    return true;
                }
                // CAS失败，重试
            }
        };

        let t1 = thread::spawn(|| deduct(50));
        let t2 = thread::spawn(|| deduct(70));

        let result1 = t1.join().unwrap();
        let result2 = t2.join().unwrap();

        // 断言：不能两个都成功（总扣款超过余额）
        assert!(!(result1 && result2), "双重扣款！");
    });
}
```

## 5. 混沌工程（Chaos Engineering）

```rust
// tests/chaos/mod.rs
use std::sync::Arc;
use tokio::sync::Mutex;
use rand::Rng;

/// 混沌实验：随机注入故障
pub struct ChaosConfig {
    pub network_latency_ms: std::ops::Range<u64>,
    pub error_injection_rate: f64,        // 0.0 - 1.0
    pub partial_response_rate: f64,
    pub connection_drop_rate: f64,
}

pub async fn chaos_test_service<F, R>(config: ChaosConfig, test_fn: F) -> R
where
    F: FnOnce(ChaosContext) -> R,
{
    let ctx = ChaosContext {
        chaos_enabled: Arc::new(AtomicBool::new(true)),
        config: Arc::new(config),
    };
    test_fn(ctx)
}

pub struct ChaosContext {
    chaos_enabled: Arc<AtomicBool>,
    config: Arc<ChaosConfig>,
}

impl ChaosContext {
    pub async fn chaos_call<F, T>(&self, f: F) -> Result<T, ChaosError>
    where
        F: std::future::Future<Output = Result<T, ChaosError>>,
    {
        // 模拟网络延迟
        let latency = rand::thread_rng()
            .gen_range(self.config.network_latency_ms.clone());
        tokio::time::sleep(Duration::from_millis(latency)).await;

        // 随机注入连接中断
        if rand::random::<f64>() < self.config.connection_drop_rate {
            return Err(ChaosError::ConnectionDropped);
        }

        f.await
    }
}

#[tokio::test]
async fn payment_service_survives_chaos() {
    let config = ChaosConfig {
        network_latency_ms: 10..2000,
        error_injection_rate: 0.1,
        partial_response_rate: 0.05,
        connection_drop_rate: 0.03,
    };

    for iteration in 0..100 {
        let result = chaos_test_service(config.clone(), |ctx| {
            async move {
                process_payment_with_chaos(&ctx, 100.0).await
            }
        }).await;

        match result {
            Ok(_) => { /* 成功 */ }
            Err(e) => {
                // 关键断言：即使在故障下，余额一致性不能破坏
                let balance = get_account_balance().await;
                let expected = calculate_expected_balance();
                assert_eq!(balance, expected,
                    "混沌测试 #{}: 账户余额不一致！", iteration);
            }
        }
    }
}
```

<details>
<summary>查看答案</summary>

**1. 属性测试 vs 单元测试：**
- 单元测试：给定具体输入A，验证具体输出B（依赖程序员想象力）
- 属性测试：描述不变量（任何输入下成立的性质），框架自动生成数百/数千个随机输入验证
- 属性测试能发现程序员未考虑的边界情况，例如整数溢出、空输入、极端长度等

**2. Fuzzing在安全Rust中的价值：**
- 安全Rust不会产生内存安全UB（Use-After-Free、Buffer Overflow等），但仍可能：
  - 逻辑panic（unwrap、expect在意外输入上失败）
  - 无限循环/栈溢出（DoS）
  - 逻辑错误（即使不crash，安全决策可能错误）
  - 性能退化（算法复杂度攻击）
- Fuzzer可发现意外panic导致的DoS和逻辑漏洞

**3. loom的原理与局限：**
- 原理：loom替换了std::sync原子操作，使用模型检查（model checking）穷举所有可能的线程交错执行顺序
- 局限：
  - 仅在测试的受限范围内穷举（需要loom::model闭包）
  - 不能用于真实系统调用（网络I/O等）
  - 状态空间随线程数和原子操作数指数增长
  - 仅覆盖loom模型内的代码路径

**4. CVE回归测试的必要性：**
- CVE代表已知的攻击向量，修复后若缺乏回归测试，后续重构可能重新引入
- 回归测试形成安全知识的制度化积累
- 新团队成员通过回归测试理解历史安全边界
- 自动化确保修复不会因依赖升级或重构而失效

**5. 混沌工程的独特价值：**
- 注入**生产环境不可预测的故障模式**：网络分区、延迟尖峰、部分故障
- 验证系统在**降级状态**下的安全行为（如"fail closed"是否正确执行）
- 发现仅在高压力/故障条件下才暴露的**非确定性安全漏洞**
- 传统测试验证正确路径，混沌工程验证错误路径的安全行为
</details>

### 二、判断题（20分，每题5分）

6. ( ) 在Rust中，由于所有权系统保证了内存安全，Fuzzing主要用于发现性能问题。
7. ( ) loom可以检测到`tokio::sync::Mutex`上的死锁。
8. ( ) 属性测试可以替代所有手工编写的单元测试。
9. ( ) 安全检查应在CI中每次PR都运行，即使会增加构建时间。

<details>
<summary>查看答案</summary>

6. **错误。** Fuzzing在安全Rust中主要发现逻辑/应用层的安全漏洞——panic导致DoS、输入验证绕过、逻辑错误等。内存安全只是安全的一部分。

7. **正确（但有限制）。** loom可以检测`loom::sync::Mutex`上的死锁（它是loom框架内的替代类型）。对于真实`tokio::sync::Mutex`，需要其他工具如`tokio-console`或`parking_lot`的deadlock detection。

8. **错误。** 属性测试是单元测试的补充而非替代。单元测试适合验证特定业务逻辑（如"VIP用户折扣应为20%"），属性测试适合验证不变量（如"折扣后价格不小于0"）。

9. **正确。** 安全检查（cargo audit、cargo deny、安全回归测试）应在每次PR中执行。这是"安全左移"的核心实践——越早发现安全问题，修复成本越低。构建时间增加是值得的代价。
</details>

### 四、编程题（15分）

11. 编写一个loom测试，验证一个线程安全的LRU缓存不会丢失条目或在并发访问下崩溃。

<details>
<summary>查看答案</summary>

```rust
use loom::sync::atomic::{AtomicU64, Ordering};
use loom::sync::Mutex;
use loom::thread;
use std::collections::HashMap;
use std::sync::Arc;

struct ThreadSafeCache {
    data: Mutex<HashMap<u64, u64>>,
    max_size: usize,
    insert_count: AtomicU64,
    get_count: AtomicU64,
}

impl ThreadSafeCache {
    fn new(max_size: usize) -> Self {
        Self {
            data: Mutex::new(HashMap::new()),
            max_size,
            insert_count: AtomicU64::new(0),
            get_count: AtomicU64::new(0),
        }
    }

    fn insert(&self, key: u64, value: u64) {
        let mut data = self.data.lock().unwrap();
        if data.len() >= self.max_size {
            // 简单LRU：删除最旧的键
            let keys: Vec<u64> = data.keys().copied().collect();
            if let Some(oldest) = keys.first() {
                data.remove(oldest);
            }
        }
        data.insert(key, value);
        self.insert_count.fetch_add(1, Ordering::SeqCst);
    }

    fn get(&self, key: u64) -> Option<u64> {
        let data = self.data.lock().unwrap();
        self.get_count.fetch_add(1, Ordering::SeqCst);
        data.get(&key).copied()
    }
}

#[test]
fn cache_concurrent_safety() {
    loom::model(|| {
        let cache = Arc::new(ThreadSafeCache::new(4));

        let c1 = cache.clone();
        let t1 = thread::spawn(move || {
            for i in 0..10 {
                c1.insert(i, i * 10);
            }
        });

        let c2 = cache.clone();
        let t2 = thread::spawn(move || {
            for i in 0..5 {
                let val = c2.get(i);
                // 值存在时应等于i*10
                if let Some(v) = val {
                    assert_eq!(v, i * 10,
                        "值不匹配：key={}, expected={}, got={}", i, i*10, v);
                }
            }
        });

        t1.join().unwrap();
        t2.join().unwrap();

        // 安全断言：insert操作不应panic或死锁
        assert!(cache.insert_count.load(Ordering::SeqCst) > 0);
    });
}
```
</details>

```rust
fuzz_target!(|data: &[u8]| {
    let start = std::time::Instant::now();
    let result = std::panic::catch_unwind(|| {
        let _: Result<serde_json::Value, _> = serde_json::from_slice(data);
```

## 本章小结

企业级安全测试远不止"跑通单元测试"。属性测试用数学不变量取代人工猜测，揭露隐藏在边界条件中的逻辑漏洞。Fuzzing作为自动化的攻击者，以不可思议的创造力生成畸形输入，即使Rust的安全保证消除了内存错误，仍可发现panic引起的DoS和逻辑绕过。

loom通过穷举线程交错，将并发安全从"看起来对"提升到"数学上对"——在金融支付等领域，这是防止百万级损失的最后防线。安全回归测试将每一次安全事件的教训固化为自动化护栏，确保漏洞不会"昨日重现"。

混沌工程将测试从实验室带入战场——在受控环境中模拟生产故障，验证系统在压力下的安全行为。这些测试方法的组合构成了"纵深防御"的测试策略：没有单一方法完美，但多层覆盖将安全缺陷的逃逸概率降到最低。

安全测试的投入与生产系统的风险成正比。对于处理敏感数据、金融交易或关键基础设施的系统，本章描述的每一层测试都并非奢侈，而是必要。
