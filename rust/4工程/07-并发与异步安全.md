# 并发与异步安全

## 企业场景

某加密货币交易所的撮合引擎在2023年"黑色星期四"期间发生重大事故：极端的市场波动触发了系统的竞态条件，同一笔USDT余额被同时用于多笔交易，导致平台在15分钟内损失$8.7M。

事故追溯发现：
1. 订单匹配和余额扣减之间存在TOCTOU窗口
2. 异步取消（Future被drop）时未正确处理回滚
3. 熔断机制触发后，仍有请求绕过了检查

本章系统性分析Rust并发/异步编程中的安全陷阱及解决方案。

## 1. 竞态条件：Double-Spend防范

### 1.1 余额扣减的经典竞态

```rust
use std::sync::atomic::{AtomicI64, Ordering};

// ❌ 有竞态条件的余额扣减
struct VulnerableBalance {
    balance: AtomicI64,
}

impl VulnerableBalance {
    fn deduct(&self, amount: i64) -> Result<(), &'static str> {
        let current = self.balance.load(Ordering::SeqCst);
        if current >= amount {
            // ⚠️ TOCTOU窗口：检查和操作之间，另一个线程可能也通过了检查
            self.balance.store(current - amount, Ordering::SeqCst);
            Ok(())
        } else {
            Err("余额不足")
        }
    }
}

// ✅ 使用CAS（Compare-And-Swap）消除竞态
struct SecureBalance {
    balance: AtomicI64,
}

impl SecureBalance {
    fn deduct(&self, amount: i64) -> Result<(), &'static str> {
        loop {
            let current = self.balance.load(Ordering::SeqCst);
            if current < amount {
                return Err("余额不足");
            }
            // CAS原子地检查当前值并执行扣减
            match self.balance.compare_exchange(
                current,
                current - amount,
                Ordering::SeqCst,
                Ordering::SeqCst,
            ) {
                Ok(_) => return Ok(()),  // 扣减成功
                Err(_) => continue,       // CAS失败 → 其他线程已修改 → 重试
            }
        }
    }

    // 使用fetch_update简化CAS循环
    fn deduct_v2(&self, amount: i64) -> Result<(), &'static str> {
        self.balance
            .fetch_update(Ordering::SeqCst, Ordering::SeqCst, |current| {
                if current >= amount {
                    Some(current - amount)
                } else {
                    None  // 余额不足 → 终止更新
                }
            })
            .map(|_| ())
            .map_err(|_| "余额不足")
    }
}

#[tokio::test]
async fn test_double_spend_prevention() {
    use std::sync::Arc;

    let balance = Arc::new(SecureBalance {
        balance: AtomicI64::new(100),
    });

    let mut handles = vec![];
    let results = Arc::new(std::sync::Mutex::new(Vec::new()));

    // 启动100个并发扣减线程，每个尝试扣减10
    for _ in 0..100 {
        let balance = balance.clone();
        let results = results.clone();
        handles.push(tokio::spawn(async move {
            let result = balance.deduct(10);
            results.lock().unwrap().push(result.is_ok());
        }));
    }

    for handle in handles {
        handle.await.unwrap();
    }

    let success_count = results.lock().unwrap()
        .iter().filter(|&&x| x).count();
    let final_balance = balance.balance.load(Ordering::SeqCst);

    // 关键断言：
    // 成功次数 = (100 - final_balance) / 10
    assert_eq!(success_count as i64, (100 - final_balance) / 10);
    assert!(final_balance >= 0, "余额不能为负");
    assert!(success_count <= 10, "最多10次成功（余额100，每次10）");
}
```

### 1.2 使用Tokio Mutex保护复杂业务逻辑

```rust
use tokio::sync::Mutex;

/// 支付引擎的原子交易处理
pub struct PaymentEngine {
    accounts: Mutex<HashMap<u64, i64>>,  // 账户ID → 余额
}

impl PaymentEngine {
    /// 执行转账——整个操作在Mutex保护下原子化
    pub async fn transfer(
        &self,
        from: u64,
        to: u64,
        amount: i64,
    ) -> Result<(), TransferError> {
        if amount <= 0 {
            return Err(TransferError::InvalidAmount);
        }

        // 🔒 持有锁的整个期间，转账是原子的
        let mut accounts = self.accounts.lock().await;

        let from_balance = accounts.get(&from)
            .ok_or(TransferError::AccountNotFound)?;

        if *from_balance < amount {
            return Err(TransferError::InsufficientFunds);
        }

        // ⚠️ 整组修改必须同时在锁内完成
        let to_balance = accounts.entry(to)
            .or_insert(0);

        *accounts.get_mut(&from).unwrap() -= amount;
        *to_balance += amount;

        // 🔒 锁在此处释放

        // 记录审计日志（在锁外，防止日志I/O阻塞其他转账）
        audit_log!(
            INFO, "transfer.completed",
            format!("user_{}", from),
            "transfer",
            from_account = from,
            to_account = to,
            amount = amount,
        );

        Ok(())
    }
}

// ⚠️ 注意：Tokio Mutex的锁跨越.await点时可能导致死锁或长时间持锁
// ⚠️ 永远不要在持有tokio::sync::Mutex时调用.await
impl PaymentEngine {
    // ❌ 危险：持锁时.await
    async fn bad_transfer_with_notification(&self, from: u64, to: u64, amount: i64) {
        let mut accounts = self.accounts.lock().await;
        // ... 修改账户 ...
        // ⚠️ 持锁时发送通知——如果通知渠道阻塞，锁也被阻塞
        send_notification(to, amount).await;  // 危险！
        // accounts锁在此释放
    }

    // ✅ 正确：先释放锁，再发送通知
    async fn good_transfer_with_notification(&self, from: u64, to: u64, amount: i64) {
        let result = {
            let mut accounts = self.accounts.lock().await;
            // ... 修改账户 ...
            Ok(())
        };  // 锁在此释放

        // 锁外发送通知
        if result.is_ok() {
            send_notification(to, amount).await;
        }
    }
}
```

## 2. Async取消安全

### 2.1 什么是取消安全？

```rust
use tokio::select;

/// ⚠️ 取消不安全：Future被drop时状态不一致
async fn cancel_unsafe_payment(
    engine: &PaymentEngine,
    from: u64,
    to: u64,
    amount: i64,
) -> Result<(), TransferError> {
    // 步骤1：扣减from账户（已完成）
    engine.deduct(from, amount).await?;  // ← 如果在此之后被取消...

    // 步骤2：增加to账户（未完成）
    engine.credit(to, amount).await?;    // ← from已扣钱，to没收钱→钱凭空消失

    Ok(())
}

/// ✅ 取消安全：使用事务性操作
async fn cancel_safe_payment(
    engine: &PaymentEngine,
    from: u64,
    to: u64,
    amount: i64,
) -> Result<(), TransferError> {
    // 使用数据库事务——整组操作要么全部完成，要么全部回滚
    let mut tx = engine.begin_transaction().await?;

    tx.deduct(from, amount).await?;
    tx.credit(to, amount).await?;

    tx.commit().await?;  // 如果在此之前被取消→整个事务回滚

    Ok(())
}

/// ✅ 取消安全：使用补偿操作
async fn cancel_safe_payment_with_compensation(
    engine: &PaymentEngine,
    from: u64,
    to: u64,
    amount: i64,
) -> Result<(), TransferError> {
    engine.deduct(from, amount).await?;

    // 使用tokio::select时的安全处理
    let result = tokio::select! {
        credit_result = engine.credit(to, amount) => {
            credit_result
        }
        _ = tokio::time::sleep(Duration::from_secs(30)) => {
            // 超时——回滚扣减
            engine.credit(from, amount).await?;  // 补偿操作：退还
            return Err(TransferError::Timeout);
        }
    };

    result?;
    Ok(())
}
```

### 2.2 Tokio JoinSet的结构化并发

```rust
use tokio::task::JoinSet;

/// 结构化并发：防止"遗忘"的任务泄漏
async fn process_batch_payments(payments: Vec<Payment>) -> Vec<Result<(), Error>> {
    let mut join_set = JoinSet::new();
    let mut results = Vec::with_capacity(payments.len());

    // 限制并发数——防止资源耗尽
    let semaphore = Arc::new(tokio::sync::Semaphore::new(10));

    for payment in payments {
        let permit = semaphore.clone().acquire_owned().await.unwrap();
        let engine = self.engine.clone();

        join_set.spawn(async move {
            let _permit = permit; // 持有permit直到任务完成
            engine.process(payment).await
        });
    }

    // 收集所有结果——JoinSet确保没有任务被遗忘
    while let Some(result) = join_set.join_next().await {
        match result {
            Ok(Ok(())) => results.push(Ok(())),
            Ok(Err(e)) => {
                // 处理支付失败（不需要回滚其他支付）
                tracing::warn!("支付处理失败: {}", e);
                results.push(Err(e));
            }
            Err(join_error) => {
                // ⚠️ 任务panic——JoinError包含panic信息
                // 不应将panic详情返回客户端
                tracing::error!("支付任务panic: {}", join_error);
                results.push(Err(Error::InternalError));
            }
        }
    }

    results
}
```

## 3. TOCTOU防范

```rust
use std::path::Path;

/// TOCTOU（Time-Of-Check-Time-Of-Use）防范示例

// ❌ TOCTOU漏洞：文件存在检查和打开之间，文件可能被替换
async fn vulnerable_file_access(path: &str) -> Result<Vec<u8>, Error> {
    // Time of Check
    if !Path::new(path).exists() {
        return Err(Error::FileNotFound);
    }

    // ⚠️ 攻击窗口：攻击者在此处替换文件（符号链接攻击）
    // 将文件替换为指向 /etc/shadow 的符号链接

    // Time of Use
    let contents = tokio::fs::read(path).await?;
    Ok(contents)
}

// ✅ 防护方案1：打开后检查（使用文件描述符）
async fn safe_file_access_v1(path: &str) -> Result<Vec<u8>, Error> {
    let file = tokio::fs::File::open(path).await?;

    // 打开后检查元数据（使用文件描述符而非路径）
    let metadata = file.metadata().await?;

    // 验证文件类型（防止符号链接）
    if !metadata.is_file() {
        return Err(Error::NotRegularFile);
    }

    // 验证归属和权限
    #[cfg(unix)]
    {
        use std::os::unix::fs::MetadataExt;
        // 文件不得有suid/sgid位
        if metadata.mode() & 0o6000 != 0 {
            return Err(Error::UnsafeFilePermissions);
        }
    }

    // 使用已打开的文件句柄读取（不被后续符号链接替换影响）
    let mut contents = Vec::new();
    tokio::io::AsyncReadExt::read_to_end(&mut file, &mut contents).await?;
    Ok(contents)
}

// ✅ 防护方案2：使用faccessat/openat2系统调用
// Rust标准库暂不支持openat2，但可以libc封装
#[cfg(target_os = "linux")]
async fn safe_file_access_v2(dir_fd: i32, filename: &str) -> Result<Vec<u8>, Error> {
    use std::ffi::CString;

    let c_filename = CString::new(filename)?;
    let fd = unsafe {
        libc::openat(
            dir_fd,
            c_filename.as_ptr(),
            libc::O_RDONLY | libc::O_NOFOLLOW | libc::O_CLOEXEC,
        )
    };

    if fd < 0 {
        return Err(Error::FileNotFound);
    }

    // 使用fd读取...
    Ok(Vec::new())
}
```

## 4. 资源耗尽防护（DoS防范）

```rust
use tokio::sync::Semaphore;
use std::sync::Arc;

/// 连接数限制——防止连接耗尽DoS
pub struct ConnectionLimiter {
    semaphore: Arc<Semaphore>,
    max_connections: usize,
}

impl ConnectionLimiter {
    pub fn new(max_connections: usize) -> Self {
        Self {
            semaphore: Arc::new(Semaphore::new(max_connections)),
            max_connections,
        }
    }

    /// 获取连接许可（阻塞直到有可用槽位，或超时）
    pub async fn acquire_with_timeout(
        &self,
        timeout: Duration,
    ) -> Result<ConnectionGuard, LimitError> {
        match tokio::time::timeout(
            timeout,
            self.semaphore.clone().acquire_owned(),
        ).await
        {
            Ok(Ok(permit)) => Ok(ConnectionGuard { _permit: permit }),
            Ok(Err(_)) => Err(LimitError::SemaphoreClosed),
            Err(_) => {
                // 超时——可能正在遭受连接泛洪攻击
                tracing::warn!(
                    security_event = true,
                    event_type = "connection_limit_reached",
                    active = self.max_connections,
                    "连接数达到上限"
                );
                Err(LimitError::TooManyConnections)
            }
        }
    }
}

pub struct ConnectionGuard {
    _permit: tokio::sync::OwnedSemaphorePermit,
}
```

### 4.1 背压（Backpressure）机制

```rust
use tokio::sync::mpsc;

/// 实现背压：当下游消费者变慢时，生产者必须等待
pub struct BackpressureProcessor {
    // 有界通道：缓冲区满时sender必须等待
    sender: mpsc::Sender<WorkItem>,
    receiver: Mutex<mpsc::Receiver<WorkItem>>,
}

impl BackpressureProcessor {
    pub fn new(buffer_size: usize) -> Self {
        let (tx, rx) = mpsc::channel(buffer_size);
        Self {
            sender: tx,
            receiver: Mutex::new(rx),
        }
    }

    /// 提交工作项——如果缓冲区满，此方法会等待
    /// 这自然地限制了生产者速度
    pub async fn submit(&self, item: WorkItem) -> Result<(), ProcessError> {
        // 如果缓冲区满（下游处理不过来），send会等待
        // 这使得背压向上游传播
        self.sender.send(item).await
            .map_err(|_| ProcessError::ProcessorShutdown)
    }

    /// 启动消费者
    pub async fn start_consumer(&self) {
        let mut rx = self.receiver.lock().await;
        while let Some(item) = rx.recv().await {
            tokio::spawn(async move {
                process_item(item).await;
            });
        }
    }
}
```

## 5. 死锁防范

```rust
use std::collections::HashSet;
use std::sync::Mutex as StdMutex;

/// 死锁场景1：锁顺序不一致
struct DeadlockProne {
    a: StdMutex<i32>,
    b: StdMutex<i32>,
}

impl DeadlockProne {
    fn operation1(&self) {
        let _a = self.a.lock().unwrap();
        // 如果线程2持有b，这里等待b→可能死锁
        let _b = self.b.lock().unwrap();
    }

    fn operation2(&self) {
        let _b = self.b.lock().unwrap();
        // 如果线程1持有a，这里等待a→死锁！
        let _a = self.a.lock().unwrap();
    }
}

// ✅ 解决方案：锁顺序一致性
// 总是按固定顺序获取锁（如按锁的内存地址排序）
struct DeadlockFree {
    a: StdMutex<i32>,
    b: StdMutex<i32>,
}

impl DeadlockFree {
    fn operation1(&self) {
        // 总是先获取a，再获取b
        let _a = self.a.lock().unwrap();
        let _b = self.b.lock().unwrap();
    }

    fn operation2(&self) {
        // 同样先获取a，再获取b
        let _a = self.a.lock().unwrap();
        let _b = self.b.lock().unwrap();
    }
}
```

## 6. 线程Panic隔离

```rust
use std::panic::{self, AssertUnwindSafe};

/// Panic隔离模式：防止一个任务的panic摧毁整个进程
pub struct PanicIsolator;

impl PanicIsolator {
    /// 在隔离中运行任务——即使panic也不会crash进程
    pub async fn run_isolated<F, T, E>(
        task_name: &str,
        f: F,
    ) -> Result<T, IsolationError>
    where
        F: std::future::Future<Output = Result<T, E>> + Send + 'static,
        E: std::fmt::Debug,
    {
        let handle = tokio::spawn(async move {
            // catch_unwind捕获panic，防止传播
            let result = panic::catch_unwind(AssertUnwindSafe(|| {
                // 注意：tokio::spawn已经提供了一定程度的panic隔离
                // catch_unwind提供额外一层保护
                f
            }))
            .await?;

            result
        });

        match handle.await {
            Ok(Ok(value)) => Ok(value),
            Ok(Err(business_error)) => {
                tracing::error!(
                    task = task_name,
                    error = ?business_error,
                    "任务执行失败"
                );
                Err(IsolationError::BusinessError)
            }
            Err(join_error) => {
                if join_error.is_panic() {
                    // 任务panic了——但进程仍然存活
                    let panic_info = join_error.into_panic();
                    // 尝试获取panic消息
                    let msg = panic_info
                        .downcast_ref::<&str>()
                        .map(|s| s.to_string())
                        .or_else(|| {
                            panic_info
                                .downcast_ref::<String>()
                                .cloned()
                        })
                        .unwrap_or_else(|| "unknown panic".to_string());

                    tracing::error!(
                        task = task_name,
                        panic_message = %msg,
                        "任务发生panic——已隔离"
                    );

                    // ⚠️ Panic后可能需要清理状态
                    // 例如：回滚未完成的事务
                }
                Err(IsolationError::TaskPanicked)
            }
        }
    }
}

/// AssertUnwindSafe的使用需谨慎
///
/// AssertUnwindSafe是一个零大小类型标记，告诉编译器：
/// "我保证下面的操作在panic展开后不会产生UB"
///
/// ⚠️ 错误使用可能产生逻辑漏洞：
/// - MutexGuard被panic后未释放→死锁
/// - 状态不一致（中间状态的变更未回滚）
///
/// ✅ 安全使用模式：
/// 1. 在async块边界使用（tokio::spawn自动处理）
/// 2. 使用事务性操作（全部完成或回滚）
/// 3. 在catch_unwind后显式检查状态一致性

#[derive(Debug, thiserror::Error)]
pub enum IsolationError {
    #[error("业务逻辑错误")]
    BusinessError,
    #[error("任务发生panic")]
    TaskPanicked,
}
```

## 章节考查（100分）

### 一、概念题（40分，每题8分）

1. 解释CAS（Compare-And-Swap）如何消除余额扣减中的竞态条件。
2. 什么是Async取消安全？为什么Future被drop时可能导致数据不一致？
3. 解释TOCTOU漏洞的原理及其在Rust中的防范方法。
4. 背压机制如何防止DoS（资源耗尽）？
5. 列举三种死锁防范策略。

<details>
<summary>查看答案</summary>

**1. CAS消除竞态条件：**
- 竞态条件根源：检查和修改是两步操作，之间可能有其他线程介入
- CAS将"检查+修改"合并为单个原子操作：硬件原子地比较当前值和预期值，仅在相等时修改
- CAS循环：如果比较失败（值已被其他线程修改），重新读取并重试
- 这确保了"if balance >= amount then balance -= amount"的原子性

**2. Async取消安全：**
- 取消安全指Future在完成前被drop时，系统状态仍然一致
- 危险场景：select!中一个分支完成而另一个被取消——如果被取消的Future已经完成了一半操作（如扣款但未入账）
- 解决方案：使用事务性操作（全部或无）、补偿操作（回滚已完成步骤）、使用JoinSet结构化并发

**3. TOCTOU原理与防范：**
- 攻击者利用了"检查条件"到"进行操作"之间的时间窗口
- 经典场景：检查文件属于当前用户→攻击者替换为符号链接指向/etc/shadow→程序以当前用户权限读取/etc/shadow
- 防范方法：先打开文件获取fd（检查点），再通过fd检查元数据和读取（使用点）——fd保证操作的是同一文件

**4. 背压防DoS：**
- 无背压时：生产者无限发送→队列无限增长→内存耗尽（OOM DoS）
- 有背压时：有界通道满→send阻塞→生产者被迫等待→自然限制系统吞吐量
- 背压向上游传播，迫使调用方也减速，形成全链路的流量控制
- 结合超时机制可区分正常高负载和恶意DoS

**5. 三种死锁防范策略：**
- 锁顺序一致性：总是按固定顺序获取多个锁（如按锁地址排序）
- 锁超时：使用try_lock_for，获取不到锁就放弃并重试
- 最小化锁持有时间：不在持有锁时调用.await或执行可能阻塞的操作
</details>

### 二、判断题（20分，每题5分）

6. ( ) tokio::sync::Mutex可以被同一个任务多次获取（可重入锁）。
7. ( ) 使用AtomicI64的fetch_update总是优于使用Mutex<i64>。
8. ( ) catch_unwind可以捕获所有panic，包括在unsafe中由UB引起的abort。
9. ( ) 异步取消安全仅在使用tokio::select!时需要关注。

<details>
<summary>查看答案</summary>

6. **错误。** tokio::sync::Mutex是不可重入的。同一任务尝试获取已持有的锁会导致死锁（lock会永远等待）。
7. **错误。** Atomic操作更适合单一变量的原子更新。当需要保护多个相关变量的复合操作（如转账：扣A+增B），Mutex更合适——它保护整个临界区。
8. **错误。** catch_unwind仅捕获安全的Rust panic（由panic!宏触发）。由unsafe代码中的未定义行为（UB）引起的崩溃不是panic而是程序终止（abort/segfault），无法被catch_unwind捕获。
9. **错误。** 取消安全在以下场景都需要关注：select!、tokio::time::timeout（超时取消）、JoinSet的abort/shutdown、客户端连接断开导致Future被drop等。
</details>

### 三、代码分析题（15分）

10. 分析以下异步代码的取消安全问题：

```rust
async fn process_order(db: &Database, order_id: u64) -> Result<(), Error> {
    let order = db.get_order(order_id).await?;
    db.update_status(order_id, "processing").await?;

    let payment_result = process_payment(&order).await?;
    db.update_status(order_id, "paid").await?;

    let inventory = db.get_inventory(order.product_id).await?;
    if inventory < order.quantity {
        return Err(Error::InsufficientInventory);
    }

    db.deduct_inventory(order.product_id, order.quantity).await?;
    db.update_status(order_id, "completed").await?;

    Ok(())
}
```

<details>
<summary>查看答案</summary>

**取消不安全分析：**

如果在`db.update_status(order_id, "paid")`之后被取消（select!超时、连接断开等）：
- 订单状态："paid"（已付款）
- 库存：未扣减
- 结果：用户付了钱但没有得到商品！

如果在`db.deduct_inventory(...)`之后被取消：
- 订单状态："paid"
- 库存：已扣减
- 订单状态：不是"completed"（缺少最终状态）
- 结果：库存扣了但订单未完成，需要人工处理

**修复方案（使用数据库事务）：**

```rust
async fn process_order(db: &Database, order_id: u64) -> Result<(), Error> {
    let mut tx = db.begin_transaction().await?;

    let order = tx.get_order(order_id).await?;
    tx.update_status(order_id, "processing").await?;

    let payment_result = process_payment(&order).await?;
    tx.update_status(order_id, "paid").await?;

    let inventory = tx.get_inventory_for_update(order.product_id).await?;
    if inventory < order.quantity {
        tx.rollback().await?;  // 回滚所有状态变更
        return Err(Error::InsufficientInventory);
    }

    tx.deduct_inventory(order.product_id, order.quantity).await?;
    tx.update_status(order_id, "completed").await?;

    tx.commit().await?;  // 全部成功——应用所有变更

    Ok(())
}
```
</details>

### 四、编程题（15分）

11. 实现一个并发安全的"限时令牌"系统：令牌有效期30秒，只能被使用一次（idempotent），支持高并发验证。

<details>
<summary>查看答案</summary>

```rust
use std::collections::HashMap;
use std::sync::atomic::{AtomicBool, Ordering};
use std::time::{Duration, Instant};
use tokio::sync::RwLock;

pub struct IdempotentTokenStore {
    tokens: RwLock<HashMap<String, TokenState>>,
    cleanup_threshold: usize,
}

struct TokenState {
    expires_at: Instant,
    used: AtomicBool,
}

impl IdempotentTokenStore {
    pub fn new() -> Self {
        Self {
            tokens: RwLock::new(HashMap::new()),
            cleanup_threshold: 10_000,
        }
    }

    /// 注册新令牌（由支付初始化）
    pub async fn register_token(&self, token: String) {
        let mut tokens = self.tokens.write().await;

        // 定期清理过期令牌
        if tokens.len() > self.cleanup_threshold {
            let now = Instant::now();
            tokens.retain(|_, state| state.expires_at > now);
        }

        tokens.insert(token, TokenState {
            expires_at: Instant::now() + Duration::from_secs(30),
            used: AtomicBool::new(false),
        });
    }

    /// 验证并使用令牌（幂等——只能成功一次）
    pub async fn verify_and_use(&self, token: &str) -> Result<(), TokenError> {
        let tokens = self.tokens.read().await;

        let state = tokens.get(token)
            .ok_or(Ok(TokenError::TokenNotFound))?;

        // 1. 检查过期
        if Instant::now() > state.expires_at {
            return Err(TokenError::TokenExpired);
        }

        // 2. 原子地标记为已使用（防重复使用）
        // CAS确保只有一个线程能成功
        if state.used.compare_exchange(
            false, true,
            Ordering::SeqCst, Ordering::SeqCst,
        ).is_err() {
            return Err(TokenError::TokenAlreadyUsed);
        }

        Ok(())
    }

    /// 清理过期令牌
    pub async fn cleanup_expired(&self) -> usize {
        let mut tokens = self.tokens.write().await;
        let before = tokens.len();
        let now = Instant::now();
        tokens.retain(|_, state| state.expires_at > now);
        before - tokens.len()
    }
}

#[derive(Debug, thiserror::Error)]
pub enum TokenError {
    #[error("令牌未找到")]
    TokenNotFound,
    #[error("令牌已过期")]
    TokenExpired,
    #[error("令牌已被使用")]
    TokenAlreadyUsed,
}

#[tokio::test]
async fn test_idempotent_token() {
    use std::sync::Arc;

    let store = Arc::new(IdempotentTokenStore::new());
    store.register_token("tok_abc123".to_string()).await;

    // 第一次使用→成功
    assert!(store.verify_and_use("tok_abc123").await.is_ok());

    // 第二次使用→失败（已使用）
    assert!(matches!(
        store.verify_and_use("tok_abc123").await,
        Err(TokenError::TokenAlreadyUsed)
    ));

    // 并发的重复使用
    let store = Arc::new(IdempotentTokenStore::new());
    store.register_token("tok_concurrent".to_string()).await;

    let handles: Vec<_> = (0..100).map(|_| {
        let store = store.clone();
        tokio::spawn(async move {
            store.verify_and_use("tok_concurrent").await
        })
    }).collect();

    let mut success_count = 0;
    for handle in handles {
        if handle.await.unwrap().is_ok() {
            success_count += 1;
        }
    }

    assert_eq!(success_count, 1, "100个并发请求中仅1个应成功");
}
```
</details>

### 六、代码补全（5分）

13. 补全以下使用CAS实现的线程安全计数器：

```rust
use std::sync::atomic::{AtomicU64, Ordering};

struct IdempotencyCounter {
    counter: AtomicU64,
}

impl IdempotencyCounter {
    /// 递增计数器，但如果已超过max则不变
    fn increment_bounded(&self, max: u64) -> Result<u64, u64> {
        loop {
            let current = self.counter.load(Ordering::SeqCst);
            if current >= max {
                return Err(current);
            }
            match self.counter./* 补全 */ {
                Ok(_) => return Ok(current + 1),
                Err(_) => continue,
            }
        }
    }
}
```

<details>
<summary>查看答案</summary>

```rust
match self.counter.compare_exchange(
    current,
    current + 1,
    Ordering::SeqCst,
    Ordering::SeqCst,
) {
    Ok(_) => return Ok(current + 1),
    Err(_) => continue,
}
```

关键点：`compare_exchange`原子地检查`current`是否仍等于预期值，如果是则替换为`current+1`。如果另一个线程在`load`和`compare_exchange`之间修改了值，CAS失败→重试循环。两个内存排序都用`SeqCst`确保最强的同步保证。
</details>

## 本章小结

并发安全是企业级系统的"无声杀手"——它在低负载时从不显现，在高并发压力下突然爆发，往往伴随重大财务损失。本章从竞态条件（Double-Spend）出发，展示了CAS如何将"检查+操作"合并为原子操作，消除TOCTOU窗口。

async取消安全是Rust异步编程特有的挑战：Future可以在任何.await点被drop，而此时系统状态可能处于中间态。事务性操作（数据库事务）、补偿操作（回滚已执行的步骤）、结构化并发（JoinSet）是抵御取消不安全的三重防线。

死锁、资源耗尽、panic传播——这些不是Rust独有但Rust提供了工具来防御。tokio::sync::Mutex的不可重入性、Semaphore的连接限制、有界Channel的背压机制将"防患于未然"编码到类型系统和API设计中。

记住：并发安全测试需要特殊工具——loom（穷举线程交错）、tokio-test（时间控制）、chao-engineering（故障注入）。即使在安全Rust中，正确的并发模式仍需要深思熟虑的设计。安全保证消除的是UB（数据竞争导致的未定义行为），而非逻辑层面的并发错误。
